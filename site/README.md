# The Lighthouse site

Eleventy builds the website from this repository's Markdown. Every Markdown file outside harbour/, site/ and .claude/ becomes a page at a path mirroring its own, so a new file appears on the next build.

## Build and serve locally

Needs Node 18 or later.

```
cd site
npm ci
npm run build    # writes site/_site
npm run serve    # rebuilds on change, at http://localhost:8080
npm test         # the scan and HTML rewrites, against test/fixtures/repo
```

## What the site reads

A piece (articles/*.md, articles/short/*.md) may open with a header before its `# Title`: `published` (YYYY-MM-DD; else the byline's date, else git), `summary` (for listings; else the opening paragraph), `status` (`draft` or `released`), `investigation` (an id in investigations/) and `revised` (items `YYYY-MM-DD: sentence`, shown as a notice). A blockquote beginning `**Correction, <date>.**` or `**Later evidence, <date>.**` is shown as a notice, and its date counts as the piece's latest update in listings. A piece with neither `published` nor a byline is dated by the commit that added it, so a later edit does not move it. An essay (essays/*.md) takes the same header and is laid out the same way, labelled Essay; released essays are listed at /essays/, which the navigation links once one is released. On the front page, the latest pieces close the section headed "Findings", or follow the first section when there is none, and the latest released essays close the section headed "Essays". A piece that links review notes (notes/R-*.md) shows a Reviewed badge linking to them; a draft shows none. Pages read in one of three registers: findings (articles/), essays, and records (studies/, notes/ and any document whose header is shown as facts), which are set in sans-serif. The front page's watch strip is read from notes/php-watch-log.md: its newest `## <date>` day, the latest `HH:MM UTC` in an item's bold label, and its `**Flagged for review...**` item; without the log, or a day in it, the strip is left out. A study page (/studies/<id>/) opens with its plain summary: the paragraph beginning "In short" among the first few of its write-up or brief, else the first paragraph of its Answer or Question section; then its latest checkpoint's date and own "In short" paragraph, labelled unreviewed. It is led by its write-up (studies/<id>/<id>.md), else its brief, then lists its other top-level files and, newest first and labelled unreviewed, the checkpoints in studies/<id>/checkpoints/, dated by the date and time in each file name; its last change counts every page in the folder, so a read moves it. The schedule page (/schedule/) is read from schedule/due.csv and schedule/runs.csv at build time: a done or missed row links to the first Markdown page its `ref` names, any other row to its study; every file or directory a `ref` names is a link (a page, else its source on GitHub); a row without an end date sits on the calendar on the day it was done or claimed. The front page's "This week" block, between the introduction and the lead, is read from site/this-week.md, a small dated file the scheduled run keeps (its header comment says how): `week`, `updated` and items `YYYY-MM-DD | reported or lighthouse | sentence`, each shown with its label and day and its sentence rendered as Markdown from the repository root; items dated before the week are left out, and the whole block is left out when `updated` is more than eight days before the build, so a missed update shows nothing rather than an old week. The Latest list orders released findings and essays newest first by the date each was published or last corrected, and says so above the list; a Later evidence notice or a `revised` item is shown beside a piece but does not lift it. The front page's Latest section opens with the Now box, labelled unreviewed (site/_includes/home-now.njk): the latest run; the watches read in the last week (each study whose newest checkpoint is at most seven days before the build, newest first, under the short label a `studies/<id> | label` line under `summaries:` in sections.md gives it, else its id); the proposals under proposals.md's "Started without review" and "Agreed by the keeper" headings, linked to their anchors; a "Waiting for the keeper" line, shown only when something waits: every proposal whose Status says "waiting for the keeper", wherever it sits in proposals.md, and every schedule row marked keeper (the schedule page lists the same under #keeper); and the PHP daily log's line. The latest-run line is the newest line in schedule/runs.csv, its start time, and the rows whose `by` names that run's label and that it marked done or missed, up to four, each linked to the first page its `ref` names, the rest counted with a link to the schedule; then, counted apart, the rows still waiting: those whose `by` names the run, still open and whose window had opened by the run's day (rows the run added for later are neither). Each row reads in plain words, the kind of work (brief, read, checkpoint, record, page) and the study's short label from sections.md, else a proposal's title or the page's title without its code, with the row id kept in the link's title attribute; schedule rows waiting for the keeper read the same way. A run that finished no row and left none waiting shows its own `did` text, or, where runs.csv has a `plain` column and the row fills it, that plain sentence instead. Study pages and investigation pages show a study's title without its leading code (the code stays in the breadcrumb, the address and a title attribute). A piece in no investigation that leads a section front says it is part of that section. An investigation is investigations/<id>.md with `title`, `id`, `attention`, `question`, `current`, `started`, `studies` and `pieces` (in reading order). The site's description and its address, which the Atom feed at /feed.xml uses for its links, are in site.json. The feed lists released pieces, short forms and essays.

**The front page and the reader's paths (from 13 November 2026; notes/reader-experience-plan-2026-11-13.md).** Some of the paragraph above describes the earlier front page; where they differ, this paragraph holds. The front page has fixed slots, and adding one is a keeper decision: the introduction (README.md's first paragraph; the rest of README.md is not shown); "What we've learned so far" (site/learned.md: `date`, `status`, `reviews`, items `path | headline | sentence` each retelling one released piece or essay under its topic label, and `question`, the closing line on the charter's question; shown only when `status: reviewed`, or as a marked draft in a `LIGHTHOUSE_PREVIEW=drafts` build); This week, cut to three items with a link to /this-week/, led by the day's line (`today: YYYY-MM-DD | sentence` in site/this-week.md, labelled Live, hidden two days after its date); the investigations, each card saying where it stands (its `current` account, Reviewed, else "no reviewed finding yet", Provisional, with its newest piece or essay beside that as reading), how many of its studies have open rows in the schedule, its latest read (newest checkpoint or done row) and its next (lib/investigation-now.js); and the three newest findings and essays. /this-week/ shows every item and the watch's working material (the Now box without the run and keeper lines, which stay on /schedule/). /working/ lists the working files, and the footer links it with Follow and the feed, above a key to the status badges. The header links Investigations, Findings, This week and About. Every released piece and essay has a topic label (`labels:` in sections.md; without one, its home names it and the build warns), a status, a home and a next step (lib/model.js): pieces, essays, investigations and studies open with a "you are here" line, and every released piece ends with "Read next", the next piece in its investigation's order, else its home. One status badge is used everywhere (_includes/status.njk): Reviewed, Provisional and Live. An investigation page opens with where it stands, its studies (running first, with their latest reads) and its pieces in reading order, before its own text. The front page's budget is site/budgets.json, checked by `npm test` and by `node test/measure.mjs --check` after a build; scripts/reader_view.py is the text-only reader's view used for reader-task tests (notes/reader-tasks/).

## Publish with GitHub Pages

.github/workflows/site.yml builds and deploys on every push to main. To enable it, open the repository's Settings, then Pages, and set Source to GitHub Actions. A run made before Pages was enabled fails at its Pages step; re-run it from the Actions page, or push to main again, and the next run deploys. The site appears at https://jkershaw.github.io/lighthouse/.

For a custom domain, enter it under Settings, Pages, Custom domain. At your DNS provider, point a subdomain such as www at jkershaw.github.io with a CNAME record, or an apex domain at the A and AAAA addresses GitHub's Pages documentation lists. Tick Enforce HTTPS once the certificate is issued. Deploying from Actions needs no CNAME file.

## Any other host

Any static host can serve site/_site. Below a domain's root, build with PATH_PREFIX set to that path, such as /lighthouse/.

## Home screen and offline reading

On HTTPS (or localhost), the manifest allows a browser to offer installation or Add to Home Screen. Icons are PNG renders of assets/favicon.svg at 192, 512 and 180 pixels; the light background and theme colour match the site's paper token. There is no installation prompt or tracking.

The build writes manifest.webmanifest and sw.js after generating the pages. The worker saves the front page, every top-level section front present in that build, the offline fallback, CSS, scripts and local fonts. It also saves opened pages and their illustrations, including a first visit directly to an article. HTML always goes to the network first with the HTTP cache bypassed; a saved copy is used only when the network request fails. A server error remains a server error. Static assets use the cache first.

A content hash changes the worker on each changed build. Installation fetches the new shell before activating it, refreshes saved illustrations where possible, and removes the preceding asset cache. Opened pages survive an update and are refreshed on their next online visit. Storage is bounded to 80 pages and 120 assets, apart from the protected shell (section fronts, CSS, scripts, fonts and icons); a browser may also evict saved data. Offline copies reflect the last successful visit, rather than a promise that an account is current. No background checking happens when the site is closed.

Source Serif 4 is served locally in its original regular, semibold and italic styles, alongside the interface face Source Sans 3 in regular and semibold. The font files were retrieved on 27 October 2026 through [Google Fonts' CSS endpoint](https://fonts.googleapis.com/css2?family=Source+Sans+3:wght@400;600&family=Source+Serif+4:ital,opsz,wght@0,8..60,400;0,8..60,600;1,8..60,400&display=swap) and converted from TTF to WOFF2 with fontTools. Their SIL Open Font Licenses are included for [Source Serif 4](assets/fonts/source-serif-4-LICENSE.md) and [Source Sans 3](assets/fonts/source-sans-3-LICENSE.md). Reading needs no third-party stylesheets, fonts or scripts.

`npm test` checks shell generation and prefix handling. For browser checks, install Playwright as a development tool, build, then run `npm run test:offline`. Set PLAYWRIGHT_MODULE to an absolute Playwright module path and CHROMIUM_PATH to a Chromium executable when using a preinstalled browser. The same test supports a build made with PATH_PREFIX=/lighthouse/ when that variable is also passed to the test command. It exercises Chromium's manifest and installability checks, first-visit saving, offline pages and illustrations, the fallback, fresh online HTML, a new worker and old-cache removal. Screenshots are kept in test/screenshots/offline-36/.

## The front page and section fronts

README.md selects its lead with `lead: articles/name.md` and supplies a short `deck:` in the same opening header. Only a released full finding can lead. Its first existing image supplies the illustration, original alternative text and caption; a draft or a missing illustration cannot supply an image. The publication and latest substantive update are shown beside it. The lead deck must remain true when read alone.

The four section fronts are always available at /watch/, /articles/, /essays/ and /map/. Their optional hand-set leads, ledes and short listing summaries live in [sections.md](sections.md), as repository paths rather than template constants. The scan supplies lists, dates and kinds, with drafts excluded. The daily log is labelled unreviewed wherever it is listed. Short listing summaries are editorial signposts; they do not replace a piece's full summary.

The home page shows compact section lists. All of README.md's original prose, figures and qualifications remain in the keyboard-accessible **Background and qualifications** disclosure below them, and README.md continues to read as ordinary Markdown on GitHub. Nothing in a released article is rewritten by these templates.

## Following sections and developing stories

`/follow/` lists the all-content feed, separate findings and essays feeds, reviewed watch notices, one feed per investigation and one per declared developing story. Relevant pages advertise their feeds in the head. An investigation feed includes its listed pieces, pieces whose investigation metadata names it, and released essays linking to that investigation's Markdown page. Drafts enter no feed. Every entry carries a kind and RFC 3339 publication/update dates. A source date with no time is encoded at midnight UTC, without claiming an event time. Reviewed notice feeds include dated Correction and Later evidence blocks from released full pieces and short forms; daily logs are kept out of that feed.

A Markdown file with `kind: developing story`, `account: articles/name.md` and `log: notes/name.md` declares a story, with optional `investigation:`. Its title is the page title. `watch/php.md` is the first declaration. The account must be a released full finding. Existing account notices and daily-log `## <day> <month> <year>` blocks are read without changing either source's format. Their complete Markdown is rendered relative to its original source, so source links and illustrations keep working. Same-day reviewed notices precede logs for readability, with a visible warning that this does not establish within-day order.

Every log block is labelled unreviewed on the story page and in its story feed, whose titles, summaries and categories identify working material. Reviewed notices keep a separate visual treatment and link back to stable notice anchors in the account. The source account and daily log remain the authoritative individual records. `lib/updates.js` supplies the shared date, notice and daily-entry metadata.

## Side notes

Write an inline note as `A public trace.^[The qualification, with a [source](sources.md).]` beside the sentence it qualifies. The note may contain ordinary inline Markdown, including links; it cannot contain a newline or another side note. Numbered buttons expose notes on phones by tap, Enter or Space, with their expanded state announced to assistive technology. At 1450px and wider the notes start open in the margin, with placement adjusted to keep adjacent notes apart. They can still be collapsed. Without JavaScript every note remains visible in the text, including on wide screens; print shows the notes too. Embedded source fragments use source-and-entry prefixes to keep control IDs distinct.

The convention is demonstrated in the draft `articles/drafts/reading-one-trace.md` and `test/fixtures/markdown/side-notes.md`. It has not been applied to a released piece. Adopting it in released prose requires that piece's normal review.

## Publication status and revision histories

Pieces and essays keep `status: released` or `status: draft` as the publication gate. The optional `developing: true` marks a released account that is still being followed. The optional `next-revision:` is the author's explicit statement of the next revision, shown verbatim; the site does not infer dates or plans from prose. The PHP account now declares that its next revision depends on reviewed fixed-source evidence, matching its existing stated intent.

Under a piece's byline, the site shows Draft, Developing, Revised or Released, its latest dated revision kind, and any explicit next revision. Developing takes priority over Revised; a developing account remains released and eligible for listings. The same state appears in listings and as a second Atom category under the publication-state scheme; an explicit next revision also accompanies the feed summary.

The revision history at a piece's end combines its dated Correction and Later evidence notices with `revised` header items, newest date first. Same-day items retain source order rather than invent a clock. A link labelled earlier/previous edition or version in the revision text is shown as Earlier edition; no missing edition is guessed or reconstructed. Notices link back to their anchors in the piece. The history retains complete notice text, its source links and qualifications.

## Knowledge Lineage

`/map/knowledge-lineage/` provides overview, thread and evidence levels, plus a linked record page for every admitted study and publication. Its catalogue refreshes in `prebuild` from the checked-out commit; released publications, working studies, reviews and checkpoints retain distinct roles. Reviewed navigation is separate from the original pilot baseline. Changed source hashes withhold stale interpretations while preserving links to the current records. See [maintenance](../notes/knowledge-lineage/maintenance.md) for the bounded annotation/review step and separate curation reference.

The Knowledge Lineage verification workflow runs unit, root/subdirectory link and real Chromium tests before merge. It exercises phone, tablet and desktop layouts in light and dark, native keyboard disclosures and all study pages with JavaScript disabled. Human-reader and assistive-technology validation remain separate from browser automation.
