# Where does a software update go once it is released?

At 14:48 UTC on 2 April 2026, a new version of a Python library called mcp went up on the Python Package Index, the public registry where Python's libraries are kept. The next day it was downloaded 3,201,463 times, 48 of every hundred downloads of the library that day. Yet of the nine projects we were watching around the library, the first seen to move to it did so six days after the release.

Most programs are built on libraries, code that other people wrote and that is fetched from registries like this one. A change to a library, whether a new feature, a fix or a flaw, travels outwards along the same roads. Over seven readings of public records we followed those roads from outside as far as they went: into the projects that use a library, into the log of its downloads, into the packaged copies of software that people publish to be run, and back to the moments that make a project take a new version. This is what we found, where each record stops (none of them reaches software actually running), and what is still open.

## One release, followed outwards

We began with a plain question: can a change to a library be followed from outside, using only public records? We chose mcp, the Python kit for building with the Model Context Protocol, tooling that AI agents use, and its release 1.27.0, because no other release of the library came within four weeks of it on either side. We fixed nine projects that depend on it before reading anything they did.

Software that uses a library says which versions of it will do, and it can say so in three ways. It can give a range, such as "1.0 or later", and leave the installer, the program that fetches libraries and puts them in place, to take the newest release that fits on the day. It can pin one exact version. Or it can keep a lockfile, a file where a project writes down the exact versions it has settled on. A range takes each release as it comes; a pin or a lockfile holds still until someone, or something, moves it. That difference turned out to decide almost everything that followed.

## What a project's history shows, and where it stops

A project's public history records what it asked for and when. In four weeks, the new version reached four of the nine projects; seven of the nine were drawn from projects listed as users of the new version, so that is not a rate. One moved its exact pin six days after the release and, within half an hour, put out a release of its own that required the new version, so anyone who installed that project got the new library with it: a second step, visible from end to end. That was the only second step we found. [The first reading](where-a-software-update-went.md) has the rest.

The histories show where the new version went and when. They do not show why. Each move had an ordinary account (a maintainer's habit of taking every release, a bulk refresh of locked versions, a project adopting the library for the first time) and no record gave a reason. Nor do the histories say what anyone installed or ran. A lockfile records a choice a project made for itself; what its users received was settled on their own machines.

## What the download log shows, and where it stops

The registry keeps a public log of the files people fetch from it, by version, day and installer. It was the first public record we found on the far side of a release, among the machines taking it. We read it through public copies, since the original needs a Google account.

It told a different story from the projects' histories. From the day after the release, the new version was around half of the library's downloads every day, between 45 and 71 per cent, for three weeks. What carried it, we think, was installers settling open ranges on whatever was newest at the moment they ran: about four in five of the new version's downloads came through one installer, uv, and tools that usually install from a lockfile took it far less. Nothing in that mechanism asks whether a release is a good one.

The log stops at the download. A download is not an installation, and never a run: a mirror can serve many installations from one download, and a cache installs with none. No entry can be tied to another. When that one project pinned the new version and published its own release, the 35,024 downloads of its releases over the next three weeks sank among 109 million downloads of the library's new version on the same days, three in every ten thousand. [The reading of the download log](what-a-download-shows.md) sets out how far it reaches.

## What a published image shows, and where it stops

Some projects publish a container image: a packaged environment holding an operating system, a program and every library it needs, installed once and published so that anyone can download it and run it as it is. Inside, the installer leaves a small note of each library and version it put in place. So an image is a record of an installation, the step past the download.

One program, agentcrew, showed what that record can add. Its images held the new version of mcp from 8 April, sixteen days before its own lockfile named it, because the image was built from a range without the lockfile, so each build took the newest release that fitted. Its repository, which is what we had read before, named a different version from the one its published software held. Where a project built its image from a pin or a lockfile, the image moved only when someone moved the pin. [The reading of published images](what-an-image-holds.md) follows six projects' images release by release.

The images stop at the installation. Few projects publish one: of 37 projects around the library, seven named a published image of their own, and six of those could be read without an account. An image is made to be run, and nothing in a registry says whether it was. And the name an image is published under can be moved to a new build, while the registries, read without an account, keep no history of what a name used to hold.

## Two paces

For a later release of the library, 1.28.0 of 16 June, we chose a sample of the software built on it by a rule fixed before we looked at any image, and read 49 images from 13 image repositories. The two ways of asking for a version gave two paces. Five of the six images built from an open range in the four weeks after the release held the new version, the first 2.6 days after it, keeping pace with the download log. Every one of the 29 images built from a lockfile or an exact pin held exactly the version its lockfile or pin named. The version installed follows how the software is built. Software that pins waits.

## What moves a pin

So what moves the pin? In that sample, the largest group of pins moved not after the release but a month later. On the evening of 16 July three security advisories were published against the library; a security advisory is a public notice that some versions of a library have a flaw, naming the version that fixes it. Of the 13 projects whose first move to the new version we found, six made it within 28 hours of the third advisory, four of them in changes written by Dependabot, a service on GitHub that proposes updates. [That reading](what-moves-a-pin.md) ended by asking whether pinned software in general moves on advisories rather than on releases.

It does not, or not in that form. Across four widely used libraries, urllib3, cryptography, pyjwt and starlette, we followed 102 pins to a security fix, chosen by a rule fixed before any project was read. By late September 73 had moved, the typical one about nineteen days after the fix was released. The two days after each release and the week after each advisory each brought a short spell of quicker moves, at about the same pace, and neither drew most of them. There was no burst like the one after mcp's advisories: four of the 102 moved within a day after the advisory. About half the moves were a bot's work or merged from one. [That reading](pins-move-over-weeks.md) found something else we had not expected: in every one of 68 high or critical advisories against the 200 most downloaded Python projects between late March and late August, the fix had been published on an earlier day. The fix comes first; the warning follows.

## Did the fix's own notes matter?

A move "before the advisory" is not a move before anyone knew. When pyjwt released its fix on 21 May, its changelog, the running list of changes a project keeps beside its code, began with a section headed Security and named an advisory that GitHub did not publish for another 25 days. We read the notes of the 37 fixes behind those 68 advisories: 19 said at the release that they mended a security flaw, and eleven of those named advisories GitHub had not yet published. Across fourteen libraries, one fix each, pinned software moved before the advisory at about 1.7 times the pace to fixes that said so, though no larger share of the moves came before the advisory, and two libraries carried much of the lead. With one fix for each library, the notes could not be told apart from the library ([that reading](fixes-that-said-so.md)).

So we counted thirty libraries, each once, drawn from every advisory GitHub had reviewed, of any severity, against the 500 most downloaded Python projects over five months. There are two fair ways to add up such a count, and they gave different answers. Pooled, adding every project's moves and waiting days together, the fixes that said so led under every clock and every reading of the notes we tried, counted over the whole stretch from the release to the advisory, by about one and a half times by our own rule; but resampling the libraries put that anywhere from about half to about four times. Counted library by library, asking whether the typical library whose fix said so differed from the typical silent one, we could not tell them apart. The choice that moved the answer most was which public notice counts as "the advisory": counting to an earlier record naming the same fix widened the pooled lead, while the typical libraries still did not separate beyond what chance gives. Every one of those readings was chosen after the outcomes were known, the test has little power, and nine of the 21 silent fixes among the 43, four of them among the thirty libraries, had no notes we could read at release, which is missing evidence, not silence. So the question is not settled, in either direction. [The latest reading](the-lead-was-a-few-libraries.md) explains the two ways of counting and what each shows.

## What held, and what weakened

Two explanations weakened as the readings widened. The first was that a security advisory is the moment that moves pinned software: we saw it once, in one library on one evening, and across four libraries it did not recur. The second was that fixes whose notes said so draw pinned software sooner: we saw it pooled across fourteen libraries, and across thirty we could not see it library by library, while the pooled lead became too uncertain to call.

What held, in the samples we read, is this. Software built from a range takes a new release within days, at the pace of the download log. Software built from a pin or a lockfile holds exactly what it names, and moves over weeks, when something moves it, often in a change a bot proposed. In the high or critical advisories we read, security fixes came out before their advisories, and about half of the fixes said so in their own notes. And every public record stops at an edge: a project's history at what it asked for, the download log at the download, a published image at the installation. None of them reaches a run.

What we do not know is larger. We have found no public record of what ran, and only published images, for the few projects that publish them, show what was installed. We cannot say why any single project moved when it did. We do not know whether a fix's own notes make a difference, or how much of the software built on a library installs from ranges and how much waits for a pin. The samples are small and clustered, chosen by rules fixed in advance, and a move is a change to what a project asks for, not an installation; nothing here says that any project was exposed to any flaw.

## Why a watch on AI follows ordinary software

This is ordinary software moving: maintainers, bots and installers doing routine work. Nothing here shows AI systems spreading themselves, and we were not looking for that. The library we started with is tooling that AI agents use, but nothing in these readings used it, and a handful of the changes we read carry a line saying an AI coding tool had a hand in them (nine of the 142 moves in the widest reading), which is their authors' statement and says nothing about who decided to move.

We follow it because of the question this watch is kept for. AI systems now write code, run tasks and call one another across the internet, and what they leave behind can set the next run in motion without a person choosing it. Nobody yet knows whether such activity could sustain and spread itself in ways that degrade the infrastructure everyone shares. If it ever did, it would travel on these roads: libraries, registries, installers, images, and the bots that move pins. Before anyone can say that something unusual is moving, they need to know how fast ordinary things move, and which stretches of the road nobody can see. These readings give a first answer to both: days where software takes whatever is newest, weeks where it waits for a pin, and darkness past the installation. [The xz backdoor](the-xz-backdoor.md) shows why that darkness matters: a compromise sat in public release files for about five weeks and travelled through distribution pipelines that none of the public sources we surveyed, and none of our own instruments, watches. And [what we can see of AI activity](what-we-can-see.md) shows how partial every public view is.

## What comes next

The question of whether a fix's own notes matter rests, unsettled, until there are more libraries to count than five months of advisories hold, with the choice of which notice counts as the warning fixed before anyone looks. The fast half of the road has since been measured more widely: for most of the most downloaded Python libraries a new release was half of the downloads within two days, and for eleven none was within the month we read, while in almost all of them older versions kept part of the downloads for the month ([the later reading](two-days-for-most.md)). What keeps older versions downloaded was then read for one week: old Pythons for three libraries, other libraries' limits for four, and for the rest something the download log cannot count ([the latest reading](old-versions-new-pythons.md)). Whether what stays behind holds from week to week is the next question.
