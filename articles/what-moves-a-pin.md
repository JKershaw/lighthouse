# Software built from open ranges took a new release within days; pinned software waited a month, and moved most often when a security advisory came

At 09:05 UTC on 16 July 2026, a new copy of a program called serena was built and published for anyone to download and run. Inside it was version 1.27.0 of mcp, a Python library that AI agents use, although a newer version, 1.28.0, had been out for 29 days. Eleven hours later, at 20:14 UTC, a security advisory rated high was published against the library: its server for WebSocket connections, a part the advisory itself calls deprecated, had no way to check the host and origin that a request declared. The fix was in 1.28.1, a small follow-up release from 26 June. It was the third advisory against the library that evening; the two before it, eighteen and sixteen minutes earlier, concerned flaws already fixed in an earlier release. Four minutes after the third, a bot wrote a change moving serena's pin to 1.28.1, and a person merged it at 11:31 the next morning. Fifty-four minutes after the advisory, another project's record of its versions moved to 1.28.1, in a change the same kind of bot had written. By the end of 17 July, six of the projects we were following had made the same move, a month after the release itself.

We have been following releases of this library outward. [The projects' histories](where-a-software-update-went.md) showed what each project chose, [the download log](what-a-download-shows.md) showed a new version at half of all downloads within two days, and [the published images](what-an-image-holds.md) of six projects showed what their installers actually put in place. This time we took a later release, 1.28.0 of 16 June, and read the published images of a sample of the software built on it, fixed by a rule before we read any image. The images show two paces. Those whose installer settles an open range of versions took the new release within days, keeping pace with the download log. Those built from a lockfile or an exact pin took it only when the pin moved. For most of them that was a month or more later, if it had happened at all by mid-August, and the largest group moved in the day after the advisory, most of them in changes a bot had written, rather than after the release.

## Two ways to ask for a version

Software that uses a library says which versions of it will do. It can give a range, such as "1.26 or later", and leave the installer, the tool that fetches libraries and puts them in place, to take the newest that fits on the day. Or it can hold still: name one version exactly, which is called pinning it, or keep a lockfile, a file where a project writes down the exact versions it has settled on, and install from that. A range takes each release as it comes. A pin or a lockfile stays where it is until something moves it.

A container image is a packaged environment: an operating system, a program and every library it needs, installed once and published so that anyone can download it and run it as it is. For every Python library installed, the installer leaves a small folder inside the image whose name gives the library and its version. The image records when it was built, and its recipe shows how it installed: from a range, a pin or a lockfile. So one image tells us both how the software asked for the library and what it got.

## A sample fixed before we looked

A public index of dependencies, Open Source Insights, lists the packages that depend directly on each version of a library. We took its lists for 1.28.0, for 1.28.1 and for the version just before them, so as not to pick only software that had already moved: 199 packages in all. We put them in an order set by a scrambled form of each name, which nobody could steer, and screened the first 120. Of those, 22 named a published image of their own. We read the images built in the four weeks either side of the release, and the nearest one outside on each side, streaming each image's layers from the registry until the installer's folder for mcp appeared. Thirteen image repositories, each the published images of one program, gave us an installed version: 49 images in all. We read everything on 26 September 2026, two and a half to four months after the builds in those weeks.

## Ranges moved within days

Of the six images we read that were built from an open range in the four weeks after the release, five held 1.28.0 or 1.28.1. The first was an image of mcp-proxy-for-aws, built on 19 June, 2.6 days after the release. That is the pace of the download log. On the day after the release, the new version was 46.7 per cent of all the library's downloads from the Python Package Index, and on each day of the four weeks after it, between 43.2 and 62.0 per cent. The one exception was chemgraph, which asks for mcp without naming any version, and whose images held 1.16.0, a much older one, before the release and after it. Something else in how it settles its versions held mcp back; we did not look into what.

These images also ran ahead of their own projects. mcp-proxy-for-aws keeps a lockfile, but its image installs without it. The lockfile named 1.24.0 until 17 July; the images had held 1.28.0 since 19 June, 27.8 days earlier. mcp-pinot's images were 8.8 days ahead of its lockfile. We had seen this once before, in a single project. Here it is in all three of the projects in the sample whose images install from a range while their repository keeps a lockfile (in the third, only in an image from January), and 10 of the 20 open-range images we read held a newer mcp than their own project's lockfile named.

## Pins waited

Every one of the 29 images we read that was built from a lockfile or an exact pin held exactly the version its lockfile or pin named. Ten of them were built in the four weeks after the release, and seven of those held the new version, but all seven came from two projects whose pin had already moved. better-telegram-mcp's lockfile was moved by Renovate, a bot that proposes updates, 16 hours after the release, and its image built the next day held 1.28.0. mcp-mesh pinned 1.28.1 on 7 July, after its images had already taken it through a range. Elsewhere the pins held. mcp-atlassian's images of 10 and 11 July, more than three weeks after the release, held 1.26.0, as its lockfile said. browser-use's of 20 June held 1.26.0, its pin. serena's of 16 July held 1.27.0.

## A month later, an advisory

We found the first commit naming 1.28.0 or 1.28.1 for 13 of the projects in the sample. Six of those commits came in the 28 hours after the advisory, between 54 minutes and 27.6 hours after it, and about a month after the release. Four of the six were changes written by Dependabot, a service on GitHub that opens updates to a project's dependencies: three were committed under its name, and one was merged by a person from the branch it had opened. A fifth was made under a project's own bot account, with a person named as co-author, in a change whose message says it upgrades a different library to a new major version, with mcp moving inside it. The sixth was a person whose message says the change fixes "3 high-severity CVEs", the numbered public records of security flaws, and names all three of that evening's advisories.

The images followed their pins. mcp-atlassian's next image, built 42 minutes after its lockfile moved, held 1.28.1. So did the one image of seclab-taskflow-agent we read, built three days after its pin moved, and openroad-mcp's next image, eleven days after. The other seven first commits came at other times: better-telegram-mcp's the day after the release, langflow's a week after, mcp-mesh's three weeks after, and four more between 40 and 57 days after. Five projects in the sample had no commit naming the new release by 15 August, where our reading of their histories stopped.

*Images built from a range took the release within days; images built from a pin waited for the pin, and six of the nine pins shown moved within 28 hours of the advisory.*

We think the advisories are what moved those six. The record shows the timing, not the reason. The bot's messages say only that they bump mcp to 1.28.1, not whether they did it as a security update, though the change for serena was written within four minutes of the third advisory. The message that mentions CVEs names all three, so that project moved on the set, of which only the third needed 1.28.1 rather than an earlier release. And the change made under a project's own bot account says it upgrades a different library, with mcp moving inside it. Nor does any of this say that a project was at risk. The third advisory concerns one part of the library, which its own text calls deprecated and says most servers do not use; we did not check whether any of these projects uses that part, or the parts the other two concern, and nothing here says that any of them, or any image, was exposed.

## Where the reading runs thin

The sample is small and clustered: 49 images from 13 repositories, 23 of them from three projects. It comes from what the index lists, at most 100 dependents for each version, and projects that publish images are a group of their own. We set ourselves a limit on how much image data to download, and spent most of it before we reached Docker Hub. Of the seven repositories in the sample there, including the largest projects in it, langflow, browser-use and jesse, only browser-use gave us an installed version. langflow's lockfile says its images would have held the new release from about a week after it, but that is what its file says, not what we saw installed.

An image is also an installation made to be run, not a run. Nothing in a registry says whether an image was started, where, or how often. And a published name can be moved to a new image without leaving a trace we could read, so an image that was only ever published under a moving name, such as "latest", and then replaced, is missing from what we saw.

## What moves a pin

So the version installed follows how the software is built, as it did in the six projects before, and now in a sample chosen before we looked. Software that asks for a range got the new release as fast as the downloads did, whatever its own lockfile said. Software that pins waited for someone, or something, to move the pin, and the commonest moment for that here was not the release but the advisories a month after it, with a bot writing most of those changes. If that holds more widely, a release reaches pinned software mostly when there is a security reason to take it, and the download log, which moves with the ranges, would not show it.

Thirteen repositories cannot say whether it holds more widely. We think the next question is whether pinned software in general moves on security advisories rather than on releases. The public histories of the software built on several libraries, set against the times their advisories were published, could answer that without reading a single image.
