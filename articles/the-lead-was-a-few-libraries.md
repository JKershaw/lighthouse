# Does pinned software move sooner to a security fix that says so? Added up, it leans that way; library by library, we cannot tell

When a library mends a security flaw, the fix usually comes out before the public warning about it. On 21 May 2026, pyjwt, a Python library that many websites use to check the signed tokens that keep people logged in, released a fix whose changelog, the running list of changes a project keeps beside its code, began with a section headed Security. It named an advisory that GitHub would not publish for another 25 days. For those weeks, anyone who read the notes had been told, and anyone waiting for the advisory had not.

So it matters whether software that depends on a library takes a fix sooner when the fix says what it is. If it does, a project's own notes are a warning that works, and writing them plainly gets a fix into use sooner. If it does not, writing them plainly changes little. [An earlier reading](fixes-that-said-so.md), across fourteen libraries with one fix each, found pinned software moving before the advisory at about 1.7 times the pace to fixes that said so, and warned that two libraries carried much of it.

So we counted thirty libraries, each once. The answer is not settled. Added up across every project we followed, the fixes that said so were taken up faster before the advisory, under every clock and every reading of the notes we tried, counted over the whole stretch from the release to the advisory. Counted one library at a time, we could not tell the two kinds apart. And the answer moved most with which public notice we counted as the warning, and we tried the alternatives only after seeing the results.

*27 September 2026 · Lighthouse*

## Thirty libraries, one fix each

Software that uses a library can pin one exact version of it, or keep a lockfile, a file where a project writes down the exact versions it has settled on. Either way it holds still until someone, or something, moves it. A security advisory is a public notice that some versions of a library have a flaw, naming the version that fixes it.

We took every advisory GitHub had reviewed, of any severity, published between 27 March and 27 August 2026 against the 500 most downloaded Python projects, where the fix was out at least a day before the advisory: 215 advisories, against 43 libraries. For each library we took one fix, the one whose advisory came first, and sorted it by a rule fixed before we read a single note: *announced* if its changelog, its tag message or its package description said at the release that it mended a security flaw, and *silent* otherwise. That gave 22 announced and 21 silent.

Then we followed the software that pins them. A public index, Open Source Insights, lists the packages that depend on each version of a library. For each fix we took up to 20 packages from its list for the version just before, in an order nobody could steer, kept those whose public repository pinned or locked an affected version on the day the fix came out, and read each one's history forward to its first change to the fix, up to 27 September. Thirteen libraries gave us nothing to follow, because the index listed few or no dependents of the version before their fix; in twelve of them that version had come out 16 days or less before the fix. That left 30 libraries, 18 announced and 12 silent, and 209 pairs of a repository and a library, of which 142 had moved by 27 September.

We had hoped for twenty libraries of each kind. The 500 most downloaded projects and five months of advisories did not hold them. And twelve of the 43 fixes were ones our earlier readings had already followed, so this count widens them rather than repeating them independently.

The fair measure is the pace: of the projects still waiting, how many moved each day, from the fix's release until its advisory. The share of moves that came before the advisory is not fair by itself, because the two kinds' advisories came at different distances from their fixes; for what it is worth, 36 per cent of the moves to announced fixes came before the advisory and 43 per cent of those to silent ones.

## Two ways to add it up

There are two honest ways to add up a count like this, and here they disagree.

One pools every project: add up all the moves and all the days of waiting across every library of one kind, and divide. That asks how fast the software we followed moved, taken together. But a library with many pinned projects that waited a long time weighs heavily in it, and so does a small library whose few projects happened to move at once. The other counts each library once: work out each library's own pace, and compare the typical library of one kind, the median, with the typical library of the other. That asks whether moving sooner belongs to fixes that say so in general, rather than to a few libraries.

Pooled, the fixes that said so lead. Before the advisory, 35 moves over 1,522 days of waiting, added up across the waiting projects, gave 2.3 moves a day for every hundred projects still waiting; for silent fixes, 20 moves over 1,273 days gave 1.6. That is about one and a half times, against 1.7 in our earlier reading. How far to trust it depends on which libraries we happened to have: resampling the libraries, to see how much the ratio moves, puts it anywhere from about half to about four times.

Library by library, we could not tell them apart. The typical library whose fix said so saw about 3.2 of every hundred waiting projects move each day before the advisory; the typical silent library, about 2.7. If we shuffle the two labels at random among the 30 libraries, 10,000 times over, a gap at least that large turns up 89 times in every hundred. That says the typical libraries cannot be told apart here. With thirty libraries and few moves in each, it does not show that a modest real difference is absent.

The figure shows why the two answers part. In both rows the big dots, where many projects waited a long time, sit at the slow end: nltk, whose advisory by our rule came five months after its fix, holds 691 of the announced fixes' 1,522 waiting days on its own. The fastest libraries of both kinds are small ones, with few projects or little time before the advisory, several resting on between one and five moves: tornado, gitpython, poetry and pypdf among the announced, pydantic-ai-slim, pip, awscli and fastmcp among the silent. A pooled rate follows whichever libraries happen to be large and whichever happen to be quick. It does not follow any one of them: leave any single library out and the announced fixes still lead when pooled. Leave out the three quickest announced libraries with three or more moves, tornado, gitpython and aiohttp, and the lead shrinks to 1.7 against 1.6.

The rest of the first week after a release, from the third day to the seventh, is where our earlier reading found its difference, and it does not hold here. In that window the typical announced library had no move at all: nine of the 16 with time in it had none, against about one and a half a day for the typical silent library, of 8. Pooled, the announced fixes led in that week, 3.3 on 11 moves against 2.3 on 5, but three of the 11 were to one fix, aiohttp's, whose only security words were about an earlier release's fix. Count that fix as silent, and the pooled lead in that week turns the other way, 2.6 against 3.3.

## Which notice counts as the warning

The choice that moved the answer most was which public notice we counted as the advisory. Our rule took each fix's first advisory published within our window, from 27 March, and only where the fix had come out at least a day before. That rule could not see an earlier advisory naming the same fix, and three libraries had one.

tornado, a library for building web servers, released version 6.5.5 on 10 March with notes that opened under the heading "Security fixes". GitHub published advisories for the release within two days, but before our window opened; the one our rule counted came 23 days after the release. By our rule's clock, five of tornado's six pinned projects moved "before the advisory"; only one moved before every advisory for that release. nltk's fix was named, in the record as we read it, by a critical advisory published six days before the fix itself, which is why its pinned projects spent five months "before the advisory" by our count, and pip's had one six days before its release too.

Count instead to the earliest advisory naming the fix that GitHub had reviewed, among the records we kept, and nltk and pip have no time before it at all. Then the typical announced library moved at about 3.3 of every hundred waiting projects a day against 1.3 for the silent, a gap that shuffling matches 47 times in a hundred; pooled, the announced fixes lead by 3.4 to 1.4, about 2.4 times, and resampling the libraries puts that ratio anywhere from no difference to about five times. Nor was GitHub's advisory always the first public word. For 17 of the 43 fixes, the United States' National Vulnerability Database had published the flaw earlier, by up to 23 days among the libraries we followed. Count to those dates and the pooled lead widens to about three and a half times, with a resampled range, from about 1.4 to about 7 times, that no longer reaches no difference; the typical libraries still do not part by more than shuffling gives, 47 times in a hundred.

Of the three clocks, that one is the kindest to the notes, and we chose it, like the earlier one, after seeing the results. We did not look for earlier word still, in mailing lists, vendors' posts or the projects' own discussions. A new count should settle which notice it counts as the warning before it looks at a single move.

## What we could not read

"Silent" means silent in what we read. Eight silent fixes had no notes about the release in any of the three places we looked, and a ninth's were written two months after it. Such projects often write their notes on GitHub's release pages, which refused us in our earlier reading and which we did not ask for this time, so for these nine, silence is missing evidence, not an observation. Four of them are among the thirty libraries: litellm, mcp, pydantic-ai-slim and fastmcp. Keep only the fixes whose notes we could read at the release, and the typical libraries still cannot be told apart (about 3.2 against 2.5, matched by shuffling 87 times in a hundred), while the pooled lead widens a little, to 2.3 against 1.4.

How the notes are read changes the lean too, and not always in one direction. If only fixes whose notes used a word such as security, vulnerability or CVE count as announced, so that the three counted announced only because they described the flaw itself become silent, the typical announced library moved faster, 3.7 against 0.8, though shuffling still matches that gap 28 times in a hundred. If fixes whose only security words were about an earlier release count as silent, which among these thirty moves aiohttp, the typical silent library moved faster, 4.2 against 3.2. Neither reading is far from chance, and they point opposite ways.

Four libraries let us compare the two kinds inside one library, because both an announced and a silent fix had pinned software to follow. The announced fix drew moves faster in three, cryptography, aiohttp and gitpython, and slower in the fourth, pip, but each side rests on between none and four moves.

## How much this can see

All of these readings together make 36 overlapping comparisons. Two of them pass the usual test of a result that chance would rarely give, and seven of the resampled ranges for the pooled lead stay clear of no difference, all of them under readings we chose after seeing the outcomes. We made no allowance for how many comparisons there were, and we claim none of them as a finding.

And a move is a request. It changes what a project's next build or installation would take, and says nothing about what was installed or run. Nothing here says that any project was exposed.

## What this does to what we said before

Our earlier reading said that pinned software moved faster before the advisory to fixes whose notes said so, mostly in people's changes in the week after the release, and that with one fix for each library the notes could not be told apart from the library. Counting thirty libraries, each once, does not resolve that doubt. We could not tell the typical library whose fix said so from the typical library whose fix did not, and the week that carried the earlier difference shows no difference here. The pooled count still leans the announced way, by about one and a half times by our rule and by more when earlier notices are counted, and no single library's removal changes that; but by our own rule resampling the libraries puts even the pooled lead within reach of no difference, and the readings that do not reach it were chosen after the fact. So we do not say the notes make no difference, and we do not say they make one. This sample cannot settle it.

## The next question

The question needs more libraries than the 500 most downloaded projects hold in five months: a longer window of advisories, or a way of finding pinned software that does not depend on the version before a fix having listed dependents, since the libraries that release often are exactly the ones that way loses. A new count should fix before it looks which public notice counts as the advisory, searched beyond one database, and how to treat fixes whose notes cannot be read. GitHub's release pages, read from somewhere they are served, would say whether the nine silent fixes without readable notes were silent. And whether the people who moved in the week after an announced release had read its notes is still a question for their pull requests.
