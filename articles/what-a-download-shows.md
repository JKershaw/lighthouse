# Downloads show a new release taken up within two days, but not where it was installed or whether anyone ran it

On 3 April 2026, the day after it was published, version 1.27.0 of a Python library called mcp was downloaded 3,201,463 times. That was 48 of every hundred downloads of the library that day, and on the day after, more than half. Of the nine projects we had been watching around the library, none had yet been seen to take the new version up. The first to write a requirement for exactly that version did so on 8 April.

We had followed this release before, [through the public histories of those nine projects](where-a-software-update-went.md), and the trail stopped where every public record we read stopped: at the machines where the code was installed. One public record looks past that edge, the log of files downloaded from the Python Package Index. We read it for the same four weeks. It shows the new version arriving in days, carried, we think, by the programs that install software rather than by any project's decision. And what it sees is a download: never an installation, and never a run.

*26 September 2026 · Lighthouse*

## A log of every download

The Python Package Index is the registry where Python libraries are published, and it keeps a public log of the files people fetch from it. Each entry names the library, the version, the time (the copy we read keeps only the day), the installer that asked for the file, and whether the installer said it was running on a build server. The log is the one public record we know of that sits on the far side of a release, among the people and machines taking it.

The original is held in Google's BigQuery service, which needs a Google account to read. We did not make one, so we read the log through three public copies of it, kept by ClickHouse, pypistats.org and pepy.tech. Only ClickHouse's copy reaches back to April with the version and installer of each download, so the counts below are its counts. The copies agree closely. On the 25 days of our four weeks that pypistats.org still holds, its daily totals for the library matched ClickHouse's exactly on 17 and were never more than about one per cent apart. That shows neither copy has drifted far from the other, not that either matches the original, and nothing below changes at that scale.

The registry itself is frank about what such counts are worth. Its packaging guide calls download counts "Highly inaccurate": installers' caches lower them, private mirrors can raise or lower them, and scripts can inflate them. Keep that in mind; we come back to it.

## Half of all downloads within two days

The library, mcp, is the Python kit for building with the Model Context Protocol, tooling that AI agents use. It is downloaded a great deal: between 4 and 12 million times a day in those weeks, about 220 million times in the four weeks together.

Version 1.27.0 went up on the registry at 14:48 UTC on 2 April. In the nine hours left of that day it was downloaded 1,639,539 times, 22 per cent of the day's downloads of the library. The next day it was 48 per cent, the day after 51. On every day from then to 22 April it was between 45 and 71 per cent. Over the four weeks it was downloaded about 96 million times, though it existed for only three of them. The release before it, in January, went the same way, passing 60 per cent the day after it came out, so this pace is ordinary for this library.

Set that beside the nine projects. The first to be seen holding the new version was one whose history on GitHub begins on 4 April with it already in place. The first to choose it outright, with an exact requirement, did so on 8 April. By then the new version had been about half of every day's downloads for five days. A busy project's lockfile, where a project writes down the exact versions it has settled on, took it on 13 April; a second exact requirement followed on 14 April, and a project new to the library took it on 22 April. The other five did not take it up in those weeks.

## What carried it

If the neighbours' choices did not carry the new version into those millions of downloads, what did? The log names the installer behind each one. Over the four weeks, 79 per cent of the library's downloads were made by an installer called uv and 20 per cent by pip, the installer that comes with Python. From 3 to 22 April, about four of every five downloads of the new version came through uv.

What an installer fetches depends on what it is asked for. Many projects ask for a range, such as "1.0 or later", not an exact version, and an installer meeting a range picks the newest release that fits, at the moment it runs. So a new environment set up on 3 April would have received 1.27.0 because it existed, whether or not anyone upstream had decided anything. We think that is what most of these downloads were: installers settling open ranges afresh. The log does not say so directly, but two things in it fit.

The first is which tools took the new version and which did not. From 3 to 22 April it was 59 per cent of uv's downloads of the library and 53 per cent of pip's, but 21 per cent of Poetry's and under 1 per cent of Bazel's. Poetry and Bazel are tools that usually install from a lockfile, which is meant to hold versions still until someone changes them; uv and pip can work either way, and the log does not say which way they were used. The second is the build-server flag. In the same days, only 11 per cent of the new version's downloads carried it, against 49 per cent of the previous version's and 72 per cent of all older versions' together. The flag is what an installer reports about itself, and one that reports nothing is counted as not a build server, so the true shares may be higher. Still, the pattern is the one you would expect if builds that have fixed their versions kept the old release while fresh installs took the new.

## A download, not an installation

That is as far as the log reaches. An entry records one file, served by the registry to a program that gave its name. It is not an installation. A mirror or a company proxy fetches a file once and may install it many times without the registry seeing; an installer's cache reinstalls without fetching; and a command that only fetches a file, or a scanner checking packages for problems, downloads without installing anything. Nothing in the log says whether a file was ever used, still less run. It does not say whether a person, a build server or an AI agent asked for it either. One pattern hints at machines: across three whole weeks in April, downloads of the new version fell less at weekends, to 0.88 of the weekday level, or 0.82 leaving out one unusually busy Sunday, while the old version's fell to about half. That fits environments created afresh whenever something runs, day or night; it also fits people working at weekends, and nothing in the log tells them apart.

The log also cannot connect one download to another. It keeps no field that identifies a client or a session, so two files fetched by the same machine a second apart are two unrelated entries.

That is where the second step of our earlier trail disappears. The project that pinned the new version on 8 April put out a release of its own 22 minutes later, and it and the release after it both require exactly 1.27.0. From 8 to 29 April those two releases were downloaded 35,024 times. Each of those that became an installation, unless a cache or proxy supplied the library, would have fetched mcp 1.27.0 too, and those fetches are in the log. But they sit among the 109,023,441 downloads of the new version on the same days, three in every ten thousand: fewer in three weeks than the new version's downloads usually rose or fell from one day to the next. No entry says which of them came from that project's users. The step that the registry's own records show plainly, from a library to a project that pins it and into that project's published release, is lost in the downloads. For the busy project, whose published requirement is only "1.0 or later", even the version its users received is recorded nowhere we read.

## What the record sees

So one public record does reach past the projects' decisions, and it tells a different story from theirs. A new release of a widely used library was being downloaded millions of times a day within a day or two, and on our reading not because the projects around it chose it, but because installers settling open ranges picked up whatever was newest. By the time the first neighbour chose the new version, it had been about half of every day's downloads for five days. Nothing in that mechanism asks whether a release is a good one, and we think a bad one would travel as fast.

What the log cannot do is say where those files went. It counts downloads, not installations, and never runs; it cannot tie one download to another; it cannot tell a person from an agent, and knows a build server only when the installer says so. And it is fading: one of the copies keeps only 180 days, so the four weeks we read will be gone from it after about 20 October. What was actually installed, and what ran, is kept in the environments themselves, and we have not yet found a public record that reads them.
