## Answer

In this neighbourhood the change travelled, and the public record shows where it went but not why. Within the window, four of the nine dependents' repositories came to hold the library's new release, `mcp` 1.27.0. The earliest record of it is R04's first GitHub commit, 2.1 days after publication, which already held it; the first move visible as a change came 6.2 days after publication. In one case the release went a further step: a dependent's own release, published 22 minutes after its update, pinned it for everyone who installs that dependent (observation and derived measurement, git and Open Source Insights). All four moves are explained by ordinary maintenance: a maintainer's standing habit of pinning each new release, this time 22 minutes before the project's own release, a bulk lockfile refresh, the pinning of another package's dependencies, and a first adoption. No identified bot made any of them, and no maintainer identity is shared with the library (derived measurement; interpretation for "explained").

What links the release to each move is a version string that did not exist before 2 April, together with the order of events in time. That proves which came first; it does not show that the release prompted the change (interpretation). The records connect nothing to running software. No source read says which version of the library anyone installed or ran during the window. Open Source Insights today resolves the same dependents' window-time versions to releases published in September 2026, five months later. Two exact pins that did not move within the window, and a failed resolution, complete the picture: version propagation can be read where dependents pin or commit lockfiles, cannot be read where they declare open ranges, and its cause cannot be read anywhere in these records (interpretation).

## Findings

**The only minute-precise public record of the release is the package registry's.** Open Source Insights gives `mcp` 1.27.0's PyPI publication as 2026-04-02T14:48:07Z (observation). In git, `v1.27.0` is a lightweight tag on a commit on the `v1.x` branch, committed at 2026-03-24T22:24:47Z. That commit is what git dates the release by, and it falls two days before the window opens; git holds no time for the tagging itself (observation, data/tags_in_window.csv has no library tag for that reason). Software Heritage's visits show `v1.x` already at the release commit on 25 March at 09:45 UTC, with the tag absent, and the tag present at the next visit, on 6 April at 22:44 UTC. The archive therefore places the tagging inside a window of thirteen days (observation, data/software_heritage_coverage.json). GH Archive's hour from 14:00 to 14:59 UTC on 2 April holds no event for the library's repository (observation). GitHub's own Release object could not be read (403 through the session proxy).

**Four of nine dependents moved to the release inside the window, and five did not** (observation, git; data/propagation_candidates.csv and data/mcp_state_window_start_end.csv).

The lags are derived measurements: commit time minus publication time. The five that did not move are R01, whose lockfile moved from 1.25.0 to 1.26.0 on 27 March in a refresh of 333 locked packages and stayed there; R05 and R08, pinned exactly to 1.26.0 throughout; R07, whose lockfile stayed at 1.26.0 through nine lockfile commits; and R09, with no `mcp` dependency in the window at all (observation). R05 is in frame A, so a later version of it takes up 1.27.0 after the window; R09 adds `mcp` after the window, which is how it entered frame B (observation, Open Source Insights).

**The change went a further step through the registry in one case only.** R03's pin commit was followed 22 minutes later by lean-lsp-mcp 0.26.0 on PyPI. Open Source Insights lists 0.26.0 among the dependents of `mcp` 1.27.0, and 0.26.1, published on 10 April, still requires `mcp==1.27.0` (observation). Anyone installing either version received that exact release: a second hop, visible end to end in public records (interpretation). R06's lockfile move was followed half an hour later by dartlab 0.9.11. Its published requirement at window end is still `mcp>=1.0` (Open Source Insights, 0.9.19), and an installer resolving a published package does not read the project's lockfile. So what dartlab's users received was decided at their own install time, and no source read records it (interpretation, following Python packaging's ordinary behaviour, not checked against dartlab's installers).

**Every move has an ordinary explanation, and nothing in the records points past it** (derived measurement for each test; interpretation for the conclusion).

- *Dependency-update bot.* None of the five commits in the table is by an identified bot. Dependabot made eight commits in the cohort in the window (six in R05, two in R00), none touching `mcp` (observation, data/authors_pseudonymous.csv and data/manifest_dependency_changes.csv).
- *Shared maintainer.* Across the whole histories of all ten repositories, no author identity outside the bot classes appears both in the library's history and in any dependent's. The only shared identities are bots (data/shared_identities_with_library.csv). Identity here means the commit address, so one person with two addresses would be missed.
- *Routine and release train.* R03 has moved its exact pin to the newest `mcp` release 18 times since August 2025, each time within 0.2 to 22.0 days of publication, median 3.2 days. The window's move, at 6.2 days, is one of the 18, and it preceded R03's own release 0.26.0 by 22 minutes (data/R03_mcp_pin_history.csv, data/propagation_candidates.csv). R06's move is one of 23 locked packages that changed in one commit, half an hour before one of its 35 PyPI releases in the window. R04's manifest pin is one of five packages pinned in one commit to fix another dependency's transitive versions. R02's is a first adoption whose lockfile took the newest release, as any resolution between 2 April and 8 May would have (data/propagation_candidates.csv).
- *The library's own dependency changes.* On 31 March the library added two dependencies on its default branch, `main`. Neither is among 1.27.0's direct requirements, because that release was cut from `v1.x`, and no dependent changed either package later in the window (data/library_dependency_changes.csv). A change to the library's repository and a change in what dependents receive are different events on different branches (interpretation).

Two of these commits, R04's pin and R04's first GitHub commit, carry a trailer naming an AI coding tool (observation). A trailer is the author's own declaration that a tool was involved. It says nothing about what the tool did, and its absence from the other commits says nothing either.

**The neighbourhood's activity is dominated by one repository and by unattributable authors.** Across 271 observed repository-days there were 2,508 commits, 9.25 per observed repository-day, and 143 repository-days had at least one commit (derived measurement, data/headline_figures.csv). R06 alone made 1,482 of them, 52.9 a day on every day of the window, 90 per cent under one account, and 91 per cent of its changed lines are JSON files rewritten almost line for line. Without R06 the rate is 4.22 per observed repository-day (derived). By author class, 13 commits (0.5 per cent) are by identified bots: eight by Dependabot, two by GitHub's Copilot coding agent app, two under an author identity that names Claude with its vendor's noreply address, and one by GitHub Actions. 1,625 (64.8 per cent) are by identified accounts not marked as bots, 1,481 of them R06's. 870 (34.7 per cent) are unknown (derived). 24 commits, 1.0 per cent, carry a trailer naming an AI coding tool, all of them naming Claude; none of the 24 is among the two whose author identity names it (observation, data/ai_tool_trailers.csv). No share of this activity is attributed to AI from style or volume, and none can be: R06's rate is equally consistent with automation, with a person committing generated data, or with both, and the record does not say which. Outside lockfiles and vendored paths the cohort added 8,065,850 lines and deleted 7,632,433; in lockfiles it added 77,205 and deleted 39,128 (derived).

**GH Archive's hour and git disagree in both directions** (observation, data/gharchive_hour_vs_git.csv). The hour holds 153,261 events in 35,617,941 compressed bytes. Four concern the cohort: one push and one branch deletion for R02, and two pushes for R05. On this date a PushEvent's payload holds only `before`, `head`, `push_id`, `ref` and `repository_id`, with no commit list and no size, so the number of commits in a push can only be had by asking git for the range between `before` and `head`. For R02, git holds three commits with committer times in the hour, all now on the default branch. The one push in the hour carried one of them; the other two appear in no push that hour. For R05, git's surviving history holds no commit in the hour, but GH Archive records two pushes to a branch that has since been deleted. Their commits are reachable from no branch or tag of a September clone, yet GitHub still served them by hash on 26 September (observation; a partial clone fetches missing objects on request). Three events in the hour, all forks, carry an empty repository record.

**The full window from GH Archive would be about 24 GB to fetch** (scenario, derived from one hour). The window is 672 hourly files. If every hour matched this one, they would total 23,935,256,352 compressed bytes, and parsing would take about half an hour at the 2.6 seconds this hour took on this container (data/gharchive_2026-04-02-14_summary.json, data/headline_figures.csv). Hours vary, and only one was measured. The cohort's share of the hour was 4 events in 153,261.

**Software Heritage could replace the forge for half the cohort, and not for the half that moved.** It archives five of the ten repositories as GitHub origins, R00, R05, R07, R08 and R09, and for all five the default-branch head at window end is in the archive. None of the four dependents that moved to 1.27.0 is archived as a GitHub origin, and neither is R01. Two of them, R04 and R06, turn up in a name search only as PyPI package origins, which hold released files, not git history (observation, data/software_heritage_coverage.json). For R00, 28 visits run from April 2025 to September 2026. Four fall near the window, on 25 March, 6 and 14 April, and 26 April, so the archive fixes the state at those instants and not between them (observation).

**One dependent's change happened out of view.** R04's GitHub history begins on 4 April with one commit holding the whole project, lockfile already at 1.27.0. Its PyPI release of 26 March names a GitLab repository as its source (observation). The move to 1.27.0 happened in a history that the GitHub record does not hold and this cohort does not include, so the nine days before 4 April are missing for R04, not zero (interpretation for "happened out of view").

## Method

The design is programme.md's LH002 section. The brief, written before any collection, fixed the ecosystem, the library, the window, the selection rule and the cohort (studies/LH002/brief.md, cohort.md). The window was fixed by the release before collection: seven whole days before the release day, twenty after. The library was chosen from four candidates on its own release dates only. The dependents were chosen by scripts/select_cohort.py from Open Source Insights' dependents of the release in the window (frame A) and of the release before it (frame B), by a hash order and a first-release-date rule that read no dependent's activity.

Collection on 26 September 2026, in order. Blobless clones of all ten repositories over HTTPS, 13:02 UTC. Open Source Insights package, version and dependency-graph records for each package at the version current at window start and at window end (scripts/collect_depsdev.py). The GH Archive hour holding the release, fetched at 13:15 UTC (scripts/gharchive_hour.py). Software Heritage origin lookups for all ten and the library's visit history, read at 13:24 UTC (scripts/swh_check.py). scripts/collect_git.py reads every commit reachable from any branch or tag, deduplicated by hash and placed by committer time converted to UTC, and keeps additions and deletions per file, split into lockfiles, vendored paths and other. It diffs the declared requirements of every manifest a commit touches (`pyproject.toml`, `setup.py`, `setup.cfg`, `Pipfile` and any file whose name contains `requirements` and ends `.txt`) and the locked versions in every Python lockfile. It also reads the `mcp` requirement and locked version at the last default-branch commit before window start and window end. scripts/analyse.py builds the candidate links and the tests of the ordinary explanations, and compares the GH Archive hour with git. scripts/summarise.py writes every headline figure to data/headline_figures.csv, and scripts/draw_maps.py draws both figures from the tables. Running the scripts in that order against fresh clones reproduces the tables. Anything that changed on the forge after 26 September will show as a difference, which is itself a reading.

Identity: author names and addresses were read into scratch space outside the repository and are not published. Each author is classed from the record alone. An address or name carrying a bot marker, or naming a dependency, CI or AI coding service account, is an identified bot. A GitHub noreply address with no bot marker is an identified account not marked as a bot, which the tables call a human account. Every other author is unknown. Pseudonyms (`H`, `B`, `U` with a number) are per study. The tables that carry commit hashes carry author classes only, not pseudonyms, so that a pseudonym cannot be looked up against a public commit.

Protocol notes. The cohort is as the brief fixed it; there is no amendment. Three things changed in method after the brief, each before any finding was drawn.
- R06's 1,482 window commits made per-commit blob fetches impractical, so line counts and manifests for R06 come from a second, shallow clone with contents from 1 March 2026. It holds R06's whole history, because R06's first commit is on 6 March.
- The manifest pattern first missed requirement files with a prefix, such as R08's `packages/services/full_requirements.txt`, and manifests below the first directory level; both were widened and every table was regenerated.
- A first draft of the analysis read commit messages truncated to 500 characters and missed trailers at their ends; the regenerated tables read full messages.

This agent's own token spend is not measured within the task; the driver session can price it from the transcript.

## Limits

**The cohort is selected on uptake.** Frame A holds packages that Open Source Insights resolves to the release in the window, so four movers in nine is not a rate at which dependents take up a release, and must not be read as one. Frame B's two members are the only contrast, and both are old projects that did not move. How the service defines a version's dependents is not documented on the page read, so the frame's exact meaning is uncertain.

**History read in September is the history that survived.** Branches deleted since the window, rebased or force-pushed commits and squashed pull requests are not in a September clone; R05's two pushes show that this happens inside the window. Committer time is when a commit was made, not when it was pushed or merged, and GH Archive shows the two can differ by more than an hour.

**The author classes are crude, and "unknown" is large.** A person committing under a personal or work address is unknown, however identifiable they are elsewhere; one person with two addresses counts twice. None of this says whether a person or a tool wrote a change.

**The dependency parsing is by pattern.** `setup.py` requirements are read by a regular expression; manifests at every depth are counted, including the library's example projects, so dependency-change counts for monorepos are inflated relative to a package's own requirements; only `uv.lock`, `poetry.lock` and `pdm.lock` are parsed for locked versions. A dependency change is counted once per package per file per commit.

**Sources not read.** GitHub's REST API refused anonymous reads through this session's proxy, so there are no fork flags, no GitHub Release objects and no pull-request records. GH Archive was read for one hour of 672. Software Heritage's visit history was read for one repository. The GitLab repository that R04's metadata names is outside the cohort and was not read. PyPI download records, the nearest public record of installation, were not in scope.

**No calibration.** LH001 has not run, so no reading here is interpreted through a standard candle; nothing here measures processing, traffic or deployment.

**What cannot be inferred, and why.** These readings describe public development activity: commits, manifests, lockfiles, releases and archive records. They do not establish that any version was deployed, run, or received traffic; they do not establish how important any repository is to anything running; and they do not establish what fraction of the code was produced by AI. The gap is structural (interpretation). The records that would connect a release to running software are install-time resolutions, deployment manifests and runtime inventories. They live on the machines that install and run the code, and no source read here observes those machines. Open-range requirements move that decision to install time, where it leaves no public trace. A lockfile records a resolution the project made for itself, not one its users made. A registry records what was offered, not what was taken. The dependency graph available today is re-resolved against today's releases, so it cannot stand in for the window's. Where a dependent pins exactly, the offered version is fixed and can be followed one hop further through the registry, as R03's was; that is the limit of what the public record connects.
