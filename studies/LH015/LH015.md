## Answer

**P1.** 247 of the 469 pairs, 52.7 per cent (95 per cent interval 45.9 to 59.3), keep at least one container recipe at the snapshot: **for some pairs**, by the brief's convention, with an interval that spans the one-half boundary (derived measurement). In the repository view the share is 45.3 per cent (40.1 to 50.8), **not as a rule**, a different label, also spanning the boundary; 151 of the 332 repositories keep a recipe at one of their snapshots and 150 at every one.

**P2.** Of the 166 pairs whose recipes the rules decide, 128, 77.1 per cent (68.4 to 84.4), are **from the pinned file**: some build installs L's version from a timed file and no other build takes it elsewhere. The label this share would carry, "as a rule", **does not stand**: undetermined pairs are 62 of the 247 with a recipe (25.1 per cent, above the brief's one fifth), and the two undetermined bounds carry different labels, 83.3 per cent "as a rule" with every undetermined pair counted as from the pinned file and 56.1 per cent "for some pairs" with every one counted as not. By pin class, with every label withheld for the same reason: lockfile 21 of 36, 58.3 per cent (39.0 to 76.9; bounds 78.9 and 29.6 per cent); exact pin 63 of 77, 81.8 per cent (68.9 to 91.0; bounds 83.9 and 72.4); both 44 of 53, 83.0 per cent (70.0 to 93.0; bounds 87.1 and 62.9). The repository view gives 70.0 per cent overall (61.2 to 78.2), which would read "for some pairs".

**What the classes mean.** A class is a reading of a recipe's instructions: what a build from it would be told to install, from which file, with the context the brief's rules fix. A recipe is not a build. No registry or image was read, so nothing here shows that any image exists, which recipe, if any, makes the images anyone runs, or what an image holds. Whether a build installs L at all (through extras, groups, markers or another package) is not resolved: "from the pinned file" means a step installs the project's requirements from a timed file that pins or locks L, and "not from the pinned file" means no step does and some step installs the project's requirements from elsewhere.

**How much rests on builds that never name L (R3).** 12 of the 38 pairs "not from the pinned file" are so only through builds that never name L: class 2 builds from a file not in T whose files, includes and arguments never name L, or class 3 builds whose release on PyPI does not list L. With those set aside, P2 is 128 of 154, 83.1 per cent (75.5 to 89.2) (derived measurement).

**Scale.** 38 of the 469 pairs read, 8.1 per cent (5.5 to 11.1), keep a recipe that the rules show would not take the pinned file; with every undetermined pair counted as not taking it, the share would be 100 of 469, 21.3 per cent. That is the part of the timed pins a build from the repository's own recipe would bypass, by this reading (derived measurement). The blind check of the classification (below) has not been run yet; until it is, every class and share here stands on the writer's reading alone.

## Findings

1. **Recipes (observation).** Every one of the 469 pairs was read: all 332 clones succeeded at the first attempt and every snapshot commit resolved, uniquely, with the committer time the earlier studies recorded (compared as instants). 247 pairs keep a primary recipe at the snapshot and 222 keep none; 13 of those 222 keep one only in excluded directories (`.devcontainer`, `.github`, tests, examples, docs), so R1 counts 260 (55.4 per cent, 48.9 to 61.9). Counting only files named `Dockerfile` or `Containerfile` (R2), 237 pairs keep one (50.5 per cent, 43.6 to 57.1). Of 662 distinct recipes at snapshots, 180 lie at the repository root, 141 one directory down, 181 two, 77 three and 83 deeper; 521 have the default name, 114 a prefixed name (`Dockerfile.x`), 26 a suffixed one (`x.Dockerfile`), one is a compose file's `dockerfile_inline`, and 2 are templates. 144 pairs with a recipe keep one, 44 two, 31 three, and a few monorepos many (one pair 81). Five pairs keep another build definition of the kinds the brief lists, counted, not classed.

2. **Builds at snapshots (derived measurement).** The 247 pairs' recipes give 731 builds (one per recipe, plus one per compose or workflow target or context). Class 1, from the pinned file: 280. Class 2, resolves afresh: 125 (lock unused 59, other file 64, lock absent 1, upgrade 1, inline 0). Class 3, the project's own package from the index: 38. Class 4, another pinned file: 12. Class 5, nothing of the project's requirements: 190 (no Python install 144, other named packages only 46). Class 6, undetermined: 86 (would not build 35, external 21, context 10, script not read 9, other 7, build argument 2, unreadable 2). The script decided 615 builds and the writer judged 116, each with a one-line reason in data/judgements.csv.

3. **Pair classes (derived measurement).** From the pinned file 128; not from the pinned file 38, of which 5 are mixed (a class 1 build beside a class 2 to 4 build); nothing of the project's requirements 19 (7.7 per cent of pairs with a recipe, 2.8 to 14.1); undetermined 62 (25.1 per cent, 15.6 to 35.1); no recipe 222.

4. **Behind "not from the pinned file" (derived measurement).** Of the 38 pairs, 25 have a class 2 build, 14 a class 3 build and 4 a class 4 build (a pair can have several). By sub-label, 15 pairs have a class 2 "other file" build, 8 a "lock unused" build (a timed lockfile in the build context that no step reads, the pattern LH006 and LH007 found), one "lock absent" and one "upgrade". By pin class: lockfile 15, exact pin 14, both 9.

5. **Lockfiles and pins, described, not tested.** Among the 89 decided pairs with a timed lockfile (pin class lockfile or both), 45, 50.6 per cent (36.7 to 65.1), have a build that installs from the timed lockfile itself. P2 for exact-pin pairs minus P2 for lockfile pairs is 23.5 points (1.1 to 44.9); exact pin minus all pairs with a lockfile is 8.8 points (minus 8.0 to 23.8). No test compares pin classes and no difference is a cause.

6. **Undetermined pairs (derived measurement).** The 62 undetermined pairs have class 6 builds whose reasons are: would not build 25 pairs, external 20, context 10, other 6, script not read 4, build argument 1, unreadable 1. 35 of the 62 are lockfile pairs, 17 both and 10 exact pin; this concentration was noticed after the counts (post hoc, one comparison, not tested). Part of "would not build" follows from the brief's context rule (2): a recipe that copies `.` needs nothing else in its own directory, so the rule fixes the context there, and recipes meant to be built from the repository root with `-f`, named only in scripts or documentation, then fail to find the project (aider's and forgepair's benchmark recipes, vantage6, auditize: 28 builds, 14 at snapshots).

7. **Sensitivities (derived measurement, not tests).** P2 with the main recipe alone deciding: 145 of 172, 84.3 per cent (77.1 to 90.0). Without the nine repositories LH006 or LH007 read: P1 52.4 per cent (237 of 452), P2 77.6 per cent (125 of 161). With every "may re-lock" build (36 at snapshots: `uv sync`, `uv run` or `poetry lock` without a flag that holds the lock) counted as class 2: 68.4 per cent (119 of 174, 58.3 to 77.2), and 17 pairs change class. Dropping recipes whose only install is at start changes nothing: no build's only install runs at start (19 builds install at start as well). R2's P2: 79.7 per cent (126 of 158). R3's P2 by pin class: lockfile 70.0 per cent (21 of 30), exact pin 86.3 (63 of 73), both 86.3 (44 of 51). No resample had an empty denominator for any measure.

## Method

Everything followed the brief's order. frame.py was rerun and its outputs compared before any clone. collect.py cloned the 332 repositories blobless and anonymously over HTTPS, six at a time with a 900-second timeout; none needed its retry. For each pair it verified the snapshot (`git rev-parse --verify <commit>^{commit}`, and the committer time equal to `snapshot_time` as an instant), listed the snapshot and head trees, and read every recipe candidate (primary or not), the ignore files at candidate contexts, every compose file outside vendored directories (at most 40 per commit, shallowest first), the CI workflows where a recipe exists (for contexts, files, targets and build arguments only), and the scripts, Makefile targets, requirements files, locks and manifests that install steps call or name. Every clone, file read and request is in data/read_log.csv.

The classifier (classify.py) parses each recipe (continuations, heredocs, exec forms, stages, ARG and ENV substitution, WORKDIR, COPY and ADD with `--from` and `--exclude`, RUN bind mounts, `.dockerignore` by Go `filepath.Match` with `**`, `!` and last match deciding), walks the final path in build order, maps every installer argument back through the copies to a path in the repository, and applies the brief's installer table, classes and override rule. collect.py ran the same code against the live tree and recorded every existence query, pattern match and relevant line it read (data/tree_paths.csv, data/aux_lines.csv); classify.py replays those records offline, so its output depends only on stored inputs. Recipe lines are kept as the brief's listed instructions only, each stored in parts of at most 400 characters (data/recipe_lines.csv); auxiliary files are kept as their relevant lines only. Its rules pass 27 synthetic cases (test_classify.py). The writer judged every build the script left, from the stored lines and the files the rules name at that commit only, and applied six amendments (amendments.md). Three readings follow the brief's definitions without amending them: a package installed from a third-party URL or a directory cloned in the build is another named package, not the project's requirements; `cp` and `mv` in a RUN carry a file's origin; and for pairs whose library is pip itself, `pip install --upgrade pip` upgrades L (the brief's sentence on upgrading pip assumes L is another package).

PyPI's JSON was read for the 38 class 3 snapshot builds (24 requests): the release named, else the newest non-pre-release uploaded at or before the snapshot commit's time, and L's requirement in it. The blind sample (60 builds, the first 30 script-decided and first 30 judged by the SHA-256 of `LH015-review-20260929:` followed by pair id, commit and path joined by colons, drawn from snapshot and head builds alike) was written to data/review_sample.csv, without classes, before any measure was computed. analyse.py computes every measure, view, difference and sensitivity on one set of 10,000 resamples of the 332 repositories read, drawn as lists of repository indices with `randrange` from one `random.Random(20260929)`, with LH011's percentile.

Ceilings used: 332 clone attempts (of 664); 1.84 GB of clones after reads (6 GB at once and 8 GB in all); 5,667 file reads (15,000); 24 PyPI requests (150); no further documentation page (10); blob reads from 15:57:30 to 16:28:18 UTC (two hours). Clones were deleted when the reads ended and never entered the repository.

## Limits

- A recipe is not a build, and no registry, image or published tag was read. Development, test and production recipes count alike, and a pair is "not from the pinned file" if any build is; the main-recipe sensitivity (84.3 per cent) shows how much that choice weighs. Which recipe makes the images anyone runs is not known.
- Whether L is installed at all is not resolved. R3 shows that 12 of the 38 "not from" pairs rest only on builds that never name L; lock-unused builds may install L only through another package, or not at all.
- A quarter of pairs with a recipe are undetermined, most for reasons the rules fix on purpose: the context rule (2) reads recipes that copy `.` at their own directory, artefacts built outside the recipe (`dist/`) decide others, and build arguments without defaults stay unread. The undetermined bounds are wide (56.1 to 83.3 per cent) and carry different labels, which is why no P2 label stands.
- The classifier reads literal instructions. It does not know a base image's WORKDIR or files, does not substitute shell variables set inside a RUN, splits unquoted `$(...)` substitutions, and does not follow Makefile prerequisites. Each failure of this kind surfaced as a build to judge rather than as a class, and the writer judged those from the stored lines; tox, hatch and invoke configurations were not read (their effect was judged from the recipe lines).
- The blind review has not been run. Every judged class is one agent's reading until the reviewer's classes are compared (brief, step 4).
- S1 is an estimate, not a resolution. S3 uses outcomes read before the brief and gives no cause. The interval describes variation across repositories like these, not sampling error within the frame.
