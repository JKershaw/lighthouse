## Answer

**P1.** 247 of the 469 pairs, 52.7 per cent (95 per cent interval 45.9 to 59.3), keep at least one container recipe at the snapshot: **for some pairs**, by the brief's convention, with an interval that spans the one-half boundary (derived measurement). In the repository view the share is 45.3 per cent (40.1 to 50.8), **not as a rule**, a different label, also spanning the boundary; 151 of the 332 repositories keep a recipe at one of their snapshots and 150 at every one.

**P2.** Of the 167 pairs whose recipes the rules decide, 129, 77.2 per cent (68.6 to 84.4), are **from the pinned file**: some build installs L's version from a timed file and no other build takes it elsewhere. The label this share would carry, "as a rule", **does not stand**: undetermined pairs are 68 of the 247 with a recipe (27.5 per cent, above the brief's one fifth), and the two undetermined bounds carry different labels, 83.8 per cent "as a rule" with every undetermined pair counted as from the pinned file and 54.9 per cent "for some pairs" with every one counted as not. By pin class, with every label withheld for the same reason: lockfile 21 of 37, 56.8 per cent (37.8 to 75.0; bounds 79.5 and 26.9 per cent); exact pin 63 of 77, 81.8 per cent (68.9 to 91.0; bounds 83.9 and 72.4); both 45 of 53, 84.9 per cent (72.9 to 94.3; bounds 88.6 and 64.3). The repository view gives 70.2 per cent overall (61.5 to 78.4), which would read "for some pairs".

**What the classes mean.** A class is a reading of a recipe's instructions: what a build from it would be told to install, from which file, with the context the brief's rules fix. A recipe is not a build. No registry or image was read, so nothing here shows that any image exists, which recipe, if any, makes the images anyone runs, or what an image holds. Whether a build installs L at all (through extras, groups, markers or another package) is not resolved: "from the pinned file" means a step installs the project's requirements from a timed file that pins or locks L, and "not from the pinned file" means no step does and some step installs the project's requirements from elsewhere.

**How much rests on builds that never name L (R3).** 12 of the 38 pairs "not from the pinned file" are so only through builds that never name L: class 2 builds from a file not in T whose files, includes and arguments never name L, or class 3 builds whose release on PyPI does not list L. With those set aside, P2 is 129 of 155, 83.2 per cent (75.8 to 89.3) (derived measurement).

**Scale.** 38 of the 469 pairs read, 8.1 per cent (5.5 to 11.2), keep a recipe that the rules show would not take the pinned file; with every undetermined pair counted as not taking it, the share would be 106 of 469, 22.6 per cent. That is the part of the timed pins a build from the repository's own recipe would bypass, by this reading (derived measurement).

**The blind check.** A reviewer who had not seen these classes classed 60 sampled builds: all 30 the writer judged agree, and 27 of the 30 the script decided (notes/R-0021.md). The brief's threshold, more than 3 of 30 wrong, was not crossed. The three errors traced to rules, and the driving session decided to correct them anyway; version 0.2 carries those corrections, made after the blind check. No label changed.

## Findings

1. **Recipes (observation).** Every one of the 469 pairs was read: all 332 clones succeeded at the first attempt and every snapshot commit resolved, uniquely, with the committer time the earlier studies recorded (compared as instants). 247 pairs keep a primary recipe at the snapshot and 222 keep none; 13 of those 222 keep one only in excluded directories (`.devcontainer`, `.github`, tests, examples, docs), so R1 counts 260 (55.4 per cent, 48.9 to 61.9). Counting only files named `Dockerfile` or `Containerfile` (R2), 237 pairs keep one (50.5 per cent, 43.6 to 57.1). Of 662 distinct recipes at snapshots, 180 lie at the repository root, 141 one directory down, 181 two, 77 three and 83 deeper; 521 have the default name, 114 a prefixed name (`Dockerfile.x`), 26 a suffixed one (`x.Dockerfile`), one is a compose file's `dockerfile_inline`, and 2 are templates. 144 pairs with a recipe keep one, 44 two, 31 three, and a few monorepos many (opea-project/genaicomps 81 at one snapshot, awslabs/mcp 51). Five pairs keep another build definition of the kinds the brief lists, counted, not classed.

2. **Builds at snapshots (derived measurement).** The 247 pairs' recipes give 731 builds (one per recipe, plus one per compose or workflow target or context). Class 1, from the pinned file: 281. Class 2, resolves afresh: 124 (lock unused 58, other file 64, lock absent 1, upgrade 1, inline 0). Class 3, the project's own package from the index: 38. Class 4, another pinned file: 13. Class 5, nothing of the project's requirements: 183 (no Python install 144, other named packages only 39). Class 6, undetermined: 92 (would not build 35, external 21, script not read 15, context 10, other 7, build argument 2, unreadable 2). The script decided 614 builds and the writer judged 117, each with a one-line reason in data/judgements.csv.

3. **Pair classes (derived measurement).** From the pinned file 129; not from the pinned file 38, of which 5 are mixed (a class 1 build beside a class 2 to 4 build); nothing of the project's requirements 12 (4.9 per cent of pairs with a recipe, 1.8 to 8.8); undetermined 68 (27.5 per cent, 17.6 to 38.0); no recipe 222.

## Method

Everything followed the brief's order. frame.py was rerun and its outputs compared before any clone. collect.py cloned the 332 repositories blobless and anonymously over HTTPS, six at a time with a 900-second timeout; none needed its retry. For each pair it verified the snapshot (`git rev-parse --verify <commit>^{commit}`, and the committer time equal to `snapshot_time` as an instant), listed the snapshot and head trees, and read every recipe candidate (primary or not), the ignore files at candidate contexts, every compose file outside vendored directories (at most 40 per commit, shallowest first), the CI workflows where a recipe exists (for contexts, files, targets and build arguments only), and the scripts, Makefile targets, requirements files, locks and manifests that install steps call or name. Every clone, file read and request is in data/read_log.csv.

The classifier (classify.py) parses each recipe (continuations, heredocs, exec forms, stages, ARG and ENV substitution, WORKDIR, COPY and ADD with `--from` and `--exclude`, RUN bind mounts, `.dockerignore` by Go `filepath.Match` with `**`, `!` and last match deciding), walks the final path in build order, maps every installer argument back through the copies to a path in the repository, and applies the brief's installer table, classes and override rule. collect.py ran the same code against the live tree and recorded every existence query, pattern match and relevant line it read (data/tree_paths.csv, data/aux_lines.csv); classify.py replays those records offline, so its output depends only on stored inputs. Recipe lines are kept as the brief's listed instructions only, each stored in parts of at most 400 characters (data/recipe_lines.csv); auxiliary files are kept as their relevant lines only. Its rules pass 30 synthetic cases (test_classify.py), three of them added in version 0.2 for the corrected rules. When a build has several class 2 sub-labels, the first in this order is reported: upgrade, lock absent, lock unused, other file, inline. The writer judged every build the script left, from the stored lines and the files the rules name at that commit only, and applied seven amendments (amendments.md; the seventh made after the blind check). Three readings follow the brief's definitions without amending them: a package installed from a third-party URL or a directory cloned in the build is another named package, not the project's requirements; `cp` and `mv` in a RUN carry a file's origin; and for pairs whose library is pip itself, `pip install --upgrade pip` upgrades L. For S2, a head recipe that installs from a lock not in T and absent at the snapshot is checked against LH008's rules for L and is class 4 when that lock locks L (as for P185-h3-0, agentstack), which the reviewer read the same way.

Contexts fixed by rule (1) rest on compose stanzas and workflow lines. Version 0.1 read those files but kept none of their lines, although the brief's step 1 lists both; the reviewer found the gap. 651 builds, 305 at snapshots, in 110 repositories had their contexts fixed that way. For version 0.2 those 110 repositories were cloned again (17:09 UTC, logged), read at the same snapshot commits and at the heads recorded in the first round, and their compose stanzas and workflow build lines are now kept in data/aux_lines.csv, each with a parsed record of the build it gives. classify.py checks every rule (1) context against those records: all 651 are supported. The second round needed 4 new blob reads (the rest came from the first round's scratch cache), and its clones were deleted on completion.

PyPI's JSON was read for the 38 class 3 snapshot builds (24 requests): the release named, else the newest non-pre-release uploaded at or before the snapshot commit's time, and L's requirement in it. The blind sample (60 builds, the first 30 script-decided and first 30 judged by the SHA-256 of `LH015-review-20260929:` followed by pair id, commit and path joined by colons, drawn from snapshot and head builds alike) was written to data/review_sample.csv, without classes, before any measure was computed. analyse.py draws it from the pools as they stood when it was drawn, taking a build as judged when data/judgements.csv holds a judgement made before the blind check, so the file is unchanged in version 0.2 although three builds moved between the pools (P132's two builds are now judged, and P418-h1-0 is now decided by the script). analyse.py computes every measure, view, difference and sensitivity on one set of 10,000 resamples of the 332 repositories read, drawn as lists of repository indices with `randrange` from one `random.Random(20260929)`, with LH011's percentile.

Ceilings used: 442 clone attempts (of 664); 1.84 GB of clones after the first round's reads and 1.23 GB after the second's, deleted between rounds, 3.10 GB in all (6 GB at once and 8 GB in all); 5,671 file reads (15,000); 24 PyPI requests (150); no further documentation page (10); the first round's clones and blob reads from 15:57:30 to 16:28:18 UTC and the second's within a minute of 17:09 UTC (two hours). Clones never entered the repository.

## Limits

- A recipe is not a build, and no registry, image or published tag was read. Development, test and production recipes count alike, and a pair is "not from the pinned file" if any build is; the main-recipe sensitivity (84.4 per cent) shows how much that choice weighs. Which recipe makes the images anyone runs is not known.
- Whether L is installed at all is not resolved. R3 shows that 12 of the 38 "not from" pairs rest only on builds that never name L; lock-unused builds may install L only through another package, or not at all.
- More than a quarter of pairs with a recipe are undetermined, most for reasons the rules fix on purpose: artefacts built outside the recipe (`dist/`) decide some, installs handed to scripts or playbooks outside the repository others, and build arguments without defaults stay unread. Some are undetermined by rule rather than in fact: context rule (2) reads a recipe that copies a bare `.` at its own directory, and an unmatched wildcard leaves rule (2) with no context (Findings, 6). The undetermined bounds are wide (54.9 to 83.8 per cent) and carry different labels, which is why no P2 label stands.
- The classifier reads literal instructions. It does not know a base image's WORKDIR or files, does not substitute shell variables set inside a RUN, splits unquoted `$(...)` substitutions, and does not follow Makefile prerequisites. Each failure of this kind surfaced as a build to judge rather than as a class, and the writer judged those from the stored lines; tox, hatch and invoke configurations were not read (their effect was judged from the recipe lines). An install at start from a directory a volume fills at run time (weblate's development recipe) is class 6 (other); no rule covers it.
- The blind check tested 60 builds. It found three script errors in 30, all traced to rules and corrected for every build; errors in builds the sample did not reach are not excluded. One pair outside the sample changed class through a corrected rule (P418, secure-string-cipher, not from to from the pinned file). The corrections were made after the blind check and after the counts.
- Contexts fixed by rule (1) now rest on retained lines for all 651 builds. Ignore files, scripts and manifests keep only their relevant lines, which is enough for the replay but not for rereading a file whole.
- S1 is an estimate, not a resolution. S3 uses outcomes read before the brief and gives no cause. The interval describes variation across repositories like these, not sampling error within the frame.

## Next

- Recipes that copy `.` and are built from the repository root by a script or a documented command are read at their own directory by rule (2); a later brief could let a build script's `-f` or a documented command fix the context, and should say how an unmatched wildcard is treated.
- A study that reads which recipe a repository publishes (workflows that push images, and the registries they name) would say which of these builds matter for running software, and would weight the monorepos' many recipes by use.
- The lockfile census the programme plans should count the lock-unused pattern: in this frame a timed lockfile was in the build context but unread in 58 snapshot builds.
