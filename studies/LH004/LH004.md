## Answer

A compromised release of xz-utils, a compression library that several Linux distributions link into their ssh server through distribution-specific dependencies (see the last finding), carried a backdoor from a tarball built in February 2024 into several distributions' rolling repositories before anyone recognised it (observation, drawn from the sources in Findings). Reading the case through Lighthouse's three layers: the backdoor's residue, malicious code sitting in two release tarballs, was technically public from 24 February 2024, the day version 5.6.0 was released, but nobody detected it there. What was actually detected, twice, sat in the activity layer: memory-checking errors seen in Red Hat's distributions from 4 March, which the backdoor's author answered with a purported fix on 8 March and a reworked backdoor released as 5.6.1 on 9 March, and then, on 29 March, one engineer's own ssh sessions running measurably slower and burning more CPU than they should, alongside valgrind errors on the same machines, which he traced to liblzma and disclosed the same day (observation, S14 and the timeline reconstruction, as read by R-0001). The second of these is the signal that broke the case. The first was not passed over: it was answered, by the person who had planted the backdoor, with changes that took the symptom away (observation of what S14 and the timeline record; the phrase "took the symptom away" is interpretation). Of the two, only the second maps cleanly onto a surface in LH F02's table, Processing, task wall time; the first is a correctness signal from a memory sanitiser, and F02's activity surfaces, tuned to resource consumption, have no row for it (interpretation). Propagation followed only after disclosure gave residue a name: distributions that had already built the compromised tarball reverted their packages within a day, and the case became a CVE, several advisories and a still-cited timeline within the same week (observation, Findings). No instrument Lighthouse has registered or proposed sat at any of these observation points, and the outward instruments LH F02 already names, GH Archive and Open Source Insights, watch source forges and language package ecosystems, not the Linux distribution package pipelines this case actually propagated through (interpretation). Whether an undetected case of the same kind exists today cannot be answered from this one case; it can only say what made this one detectable, which is not the same thing (interpretation, Limits).

## Findings

**The charter's own images for the three layers apply directly to this case, and are given here with their literal meaning before being used again.** Lighthouse_Founding_Charter.md (LH F01) describes activity as inference, "a ripple of light" across accumulated software, residue as the "afterglow" a ripple leaves when it changes code, configuration or data, and propagation as one afterglow lighting the next ripple somewhere else. Read plainly, without the images: activity is computation happening, residue is the altered structure and state that activity leaves behind, and propagation is that residue's influence on activity elsewhere (LH F02). In this case, a person's typing and a compiler's runs were the ripples; a modified build script and a compiled library sitting in a distribution's package repository were the afterglow; a second distribution's package builder picking up that same afterglow was the next ripple.

**The malicious code was residue from the moment it was released, and it was public.** Version 5.6.0 of xz-utils, containing the backdoor, was released on 24 February 2024, and 5.6.1 followed on 9 March 2024 (observation, timeline reconstruction at research.swtch.com/xz-timeline, read 2026-09-26; consistent with S15's own published date of the vulnerability). The tukaani.org project's own account states plainly that these two release tarballs, not the git repository itself, "contain a backdoor," and that the trigger code was "never included in the Git repository" (observation, tukaani.org/xz-backdoor/, read 2026-09-26). A widely cited community technical write-up describes the mechanism: a build-time script, `build-to-host.m4`, present only in the distributed tarball and absent from the git repository, decoded a disguised payload out of two test files that had been committed openly, `bad-3-corrupt_lzma2.xz` and `good-large_compressed.lzma`, and linked the result into the compiled `liblzma` shared library during an ordinary build (observation, gist.github.com/thesamesam/223949d5a074ebc3dce9ee78baad9e27, read 2026-09-26). Every one of these commits was on GitHub the whole time. That the residue was open to inspection from February 2024 is an observation; that nobody's inspection caught it before disclosure is also an observation; that the two facts together mean residue was not, in practice, where this case was first detected, even though it was technically the earliest-existing evidence, is this essay's interpretation.

**The first activity-layer signal that was noticed, in early March, was not recognised as malicious at the time.** The timeline reconstruction states that on 4 March 2024 "RedHat distributions start seeing Valgrind errors"; that on 8 March Jia Tan committed a "purported Valgrind fix", which it calls "a misdirection, but an effective one"; and that on 9 March the updated backdoor files, "the actual Valgrind fix", were released as 5.6.1 (observation of that reconstruction's account, research.swtch.com/xz-timeline, read 2026-09-26; the quotations as R-0001 read the page). S14 corroborates the response, though not its dates: the injected code "caused valgrind errors and crashes in some configurations", "These issues were attempted to be worked around in 5.6.1", "the exploit code was then adjusted", and the committer "communicated on various lists about the 'fixes'" (observation, S14, as quoted by R-0001). The early signal was therefore noticed and answered, by the backdoor's own author, with a release that removed the symptom rather than the cause (interpretation of the two accounts together). Version 0.1 of this study read the same reconstruction as recording only a misdirection and a change to test files, and did not connect them to the errors; see Corrections. One of the co-maintainers who later helped document the case recalls, in his own words, wondering afterwards whether he "should have looked into why I couldn't hit the reported Valgrind problems from Fedora on Gentoo," a reflection that confirms the reports existed and came from Fedora, and that he could not reproduce them on Gentoo, without giving an exact date or naming who first raised them (observation, gist.github.com/thesamesam, read 2026-09-26). The reconstruction does not say the errors came from build and test machines, and neither does S14; earlier versions of this study said so without a source. This study did not verify the 4 March start or the dates of the 8 and 9 March changes against the live git history; those rest on the reconstruction, while the errors and the 5.6.1 workaround are also in S14 (see Limits).

**The signal that actually broke the case, three weeks later, was also activity: one engineer's own machine running slower than it should.** Andres Freund posted to the oss-security mailing list on 29 March 2024 that he had noticed "logins with ssh taking a lot of CPU, valgrind errors" on a Debian sid system, and, on measuring it, found an ssh connection took around 0.8 seconds where he expected about 0.3 (observation, S14; https://www.openwall.com/lists/oss-security/2024/03/29/4, read 2026-09-26). His post places those symptoms "on Debian sid installations over the last weeks", and his measurement shows elapsed time of 0.299 seconds before and 0.807 seconds after, with the client's CPU time unchanged at 0.202 seconds, so the extra time was spent in the server (observation, S14, as read by R-0001). He traced the extra time to `liblzma`, found "the upstream xz repository and the xz tarballs have been backdoored," and described the mechanism at a level of technical detail, hijacked `crc32_resolve()`/`crc64_resolve()` function resolvers used to install an audit hook, redirecting `RSA_public_decrypt` so that authentication itself could be intercepted, that the community used to confirm and extend within hours (observation, S14). The vulnerability was published as CVE-2024-3094 the same day, with a CVSS base score of 10.0, the identifier having been assigned by Red Hat the day before, on 28 March, by the timeline reconstruction's account (observation, S15 for the publication, and the reconstruction as read by R-0001 for the assignment; S15 was read on 2026-09-26 through the NVD API at services.nvd.nist.gov, since the NVD web page itself needs scripts to render, matching the caveat already recorded against S15 in Lighthouse_Research_Design.md).

**Only one of these two activity-layer signals maps onto a surface in LH F02's table; the other exposes a limit in Lighthouse's proposed instruments.** Freund's CPU and elapsed-time reading is exactly what LH F02's Processing surface is built to record, busy core seconds and task wall time (LH F02, "Initial measurement surfaces"), read by hand with the same kind of tools LH001 proposes to instrument properly, `time` and valgrind, at the one observation point that happened to exist, his own workstation. No instrument Lighthouse has registered, and no instrument yet proposed, sat at that point; I-0002, the host sampler ticket, remains `todo` in `harbour/tickets.json` and is scoped to Lighthouse's own dispatch machine, not to an arbitrary engineer's laptop. The earlier valgrind signal is a different kind of reading altogether: a memory-checking tool reporting a correctness anomaly during an automated test run, not a resource-consumption reading. F02's four activity surfaces, Processing, Electricity, Communication and Inference, are all built around volume or occupied capacity; none has a row for a sanitiser's own error output (interpretation). The case therefore exposes a limit in Lighthouse's proposed instruments: none that Lighthouse has registered or proposed reads the output of a test or a sanitiser, so none would have recorded the earliest signal that was actually noticed, wherever it had been placed (interpretation). It does not explain why that signal was seen and not recognised as an attack. A gap in a framework written in 2026 cannot explain a judgement people made in 2024. Nor were the reports left uninvestigated: as the third finding records, the backdoor's author answered them with a purported fix and a reworked release (observation, S14 and the reconstruction). What no source this study read says is how widely the reports circulated before that answer, or who besides its author examined them, beyond one developer's note that he could not reproduce them (observation about the sources; see Limits).

**Residue's role in this case was to be carried, not to be read.** Once the compromised tarball existed, several distributions built it into their own packages within days to weeks. In part that is what a rolling-release package pipeline ordinarily does with a new upstream point release; in part they were pressed to. The timeline reconstruction records that on 27 February Jia Tan "starts emailing Richard W.M. Jones to update Fedora 40"; that on 25 March "Hans Jansen is back (!), filing a Debian bug to get xz-utils updated to 5.6.1", while more "addresses that don't otherwise exist on the internet show up to advocate for it"; and that on 28 March Jia Tan filed an Ubuntu bug to the same end (observation of the reconstruction's account, as read by R-0001). Version 0.1 gave the ordinary pipeline as the only reason; see Corrections. Fedora Rawhide and Fedora 40's pre-release, if `updates-testing` was enabled, picked up 5.6.0 shortly after its release and 5.6.1 after 9 March (observation, Red Hat, "Urgent security alert for Fedora 40 and Rawhide users," redhat.com/en/blog, read 2026-09-26; Fedora Magazine, "CVE-2024-3094: Urgent alert for Fedora Linux 40 and Rawhide users," read 2026-09-26). Debian carried the backdoor for about a month: the reconstruction records 5.6.0-0.1 added to unstable on 26 February, 5.6.0-0.2 to testing on 5 March, an update to 5.6.1 on 27 March, and a rollback on 28 March, the day before the public disclosure (observation of the reconstruction's account, as read by R-0001; Debian's own current security tracker, read 2026-09-26, no longer shows this window, see Limits). openSUSE Tumbleweed and MicroOS, and Kali Linux (if updated between 26 and 29 March), similarly carried a compromised build for some days (observation, reported consistently across the vendor and press sources in reading-list.md; no dates for openSUSE were found in any source read). Debian's stable releases and Red Hat Enterprise Linux were never affected, because neither had yet taken the new upstream version (observation, access.redhat.com/security/cve/CVE-2024-3094, read 2026-09-26; Red Hat's blog, same date). Each of these builds is a propagation link in LH F02's sense, residue (the compromised release) enabling activity elsewhere (a distribution's own build system compiling it, and thereafter its users' sshd processes running the injected code on every login attempt), not yet a surface itself. LH F02 treats such a link as a derived measurement, not an observation, until tested against records; here the test is the distributions' own advisories, which is as close to a controlled comparison as a historical case affords.

**None of Lighthouse's currently named outward instruments would have caught this propagation.** GH Archive (S5) records public GitHub events and would show the commits and the 5.6.0/5.6.1 tags, but not which distributions subsequently built them into packages. Open Source Insights (S11) resolves dependency graphs for Cargo, Go, Maven, npm, NuGet, PyPI and RubyGems, none of which is the RPM or Debian package graph this case actually propagated through; deps.dev would show nothing here at all. The record that did catch this propagation, in practice, was each distribution's own security tracker and advisory process, an instrument Lighthouse does not operate and has not yet catalogued; LH003, the survey of surveys, remains `todo` and could name this gap explicitly (interpretation).

**A small, low-volume dependency carried the whole risk, matching LH F02's own warning about authority.** The mechanism depended on one further residue fact: several distributions patch OpenSSH's `sshd` to notify `systemd` of service readiness, a patch that makes `sshd` link `libsystemd`, which in turn links `liblzma` for log compression, so that a compression library ends up in the same process as password and key authentication (observation, S14's own technical description; corroborated by the gist and by Red Hat's advisory). LH F02 states that "a permission is a relationship, not a volume" and that "a small authority-bearing connection may matter more than a high-volume stream." This dependency is exactly that: liblzma is a small, low-traffic library by any Processing or Communication reading, and its authority-bearing connection to sshd, not its size, is what made it dangerous (interpretation, though closely paraphrasing F02's own stated risk-assessment principle).

## Limits

**Survivor bias, as LH F04 itself warns.** This is a case that was detected, and detected unusually well: an engineer who happened to run valgrind and idle micro-benchmarks as routine habit, on a rolling-release system close enough to the injection that the compromised library was still installed, with an overhead, roughly half a second per login, large enough to notice by feel rather than needing a dashboard. An undetected case would lack exactly these things: a habitually suspicious observer, a system still carrying the compromised version at the moment of use, and an overhead large enough to notice without instrumentation. This study cannot say how many such cases exist, nor whether a quieter one has already run its course undetected; it can say only what made this one visible, and that a much smaller overhead, or a target further from a technically curious user base, plausibly would not have been.

**The dates of the earlier signal rest on secondary reconstruction; the signal itself does not.** The 4 March start, the attribution of the first errors to Red Hat's distributions, and the dates and descriptions of the 8 and 9 March changes come from research.swtch.com's timeline, and the Fedora origin of the reports from one co-maintainer's own gist. S14, the primary disclosure, corroborates that the injected code caused valgrind errors and that 5.6.1 attempted to work around them, but gives no date for either and does not name where the errors were first seen. This study did not clone the xz-utils git history and check commit timestamps directly, so these dates are reported as the reconstruction's account, not independently confirmed.

**Debian's security tracker was read on 2026-09-26 and shows today's state, not March 2024's.** The tracker currently lists Debian's buster, bullseye, bookworm and unstable suites as "not affected," with fixed versions recorded for bookworm's security suite, trixie and forky/sid, all versions that postdate the incident by a considerable margin. Before disclosure, by the timeline reconstruction's account, Debian's unstable suite carried the compromised releases from 26 February and testing from 5 March, moving to 5.6.1 on 27 March and rolling back on 28 March; only Debian's stable releases were unaffected then, as now. LH F02 anticipates exactly this: "documentation changes, so studies preserve the exact version they use." This study relies on the contemporaneous sources for what was true in March 2024 and states plainly that the tracker's current wording, read today, is not that same claim.

**Some details reported by secondary sources were not independently confirmed and are left out or hedged accordingly.** Andres Freund's employer at the time is reported by several secondary accounts found through search but was not confirmed against a primary source this study read directly (his own oss-security post is signed with his name and affiliation with the PostgreSQL project, not an employer), so no employer is asserted here. Exact figures for how many separate hosts or organisations ran a compromised build before reversion are not available in any source this study read; only the named distributions and their own stated windows are reported.

**No Lighthouse instrument, registered or proposed, observed any part of this case.** Every instrument attribution in Findings is an interpretation about what an instrument would have recorded had one existed at that observation point at that time; none is an observation of an actual reading, because Lighthouse did not exist as an observatory in 2021 to 2024 and has no retroactive access to any host or build system involved.

**This study's own collection cost is unmeasured**, as stated in Method, and its own preparation is Lighthouse activity that no source's own log could distinguish from ordinary traffic.
