Since its release in July 2026, the AI-powered penetration testing framework ARTEX has been abused by many threat actors to accelerate their existing workflows related to network reconnaissance, credential attacks, and web application exploitation. As of November 2026, Microsoft Threat Intelligence has observed both state-sponsored and financially motivated threat actors such as Storm-0940 [103], Storm-3358 [104], Onyx Sleet [105], Pearl Sleet [106], Crystal Typhoon, and Salt Typhoon integrating ARTEX into their tooling.
In the past few weeks, we’ve reported several distinct campaigns that abused ARTEX to search public repositories for exposed secrets, enable supply chain compromise, and scan internet-facing systems for exploitation. These campaigns illustrate how threat actors use ARTEX to automate various stages of the attack chain. Threat actors define scope and targets for ARTEX, which then uses AI agents to set verifiable goals, define tactical steps for each stage of the operation, use tools to attack targets, create graphs to track discovered systems and results of actions, and report back to the threat actor. Depending on the threat actor’s configuration and the target’s defenses, ARTEX can advance from reconnaissance to persistent, privileged access to a target organization in a matter of minutes.
ARTEX does not introduce new attack techniques; it uses common, pre-existing penetration testing tools and techniques. ARTEX does sometimes transmit distinctive characteristics associated with its integrated penetration testing tools. However, threat actors using ARTEX can and do vary network indicators like source IP address or user agent string, especially to bypass static or simple signature-based detection and blocking. The most reliable and durable signal of ARTEX activity is behavioral: ARTEX sends a wide variety of requests in a brief time and retries variations on the same technique or moves on to next-stage actions at machine speed.
In this blog, we’re sharing a detailed breakdown of ARTEX, including its architecture and capabilities, as well as guidance for identifying related network and system activity. Microsoft disrupts and contains threats posed by ARTEX-enabled attacks across the Microsoft Defender suite of products. Defenders can further reduce and mitigate the effectiveness of ARTEX and similar AI agentic attacks by following Microsoft’s recommendations outlined in this report to reduce internet-facing exposure, secure credentials and secrets, and limit lateral movement paths in their environment. Additionally, Microsoft recommends customers to enable automatic attack disruption in Microsoft Defender XDR to contain and isolate affected devices during an attack.
To help defenders keep pace with machine-speed attacks, Microsoft Perception [107] coordinates red, blue, and green team agents that find exploitable weaknesses, investigate threats, and remediate risks, with security teams approving critical actions. As threat actors increasingly adopt AI, we’re publishing this information to equip defenders with insights that can help protect systems, secrets, identities, and networks from AI-assisted attacks.
## ARTEX: Publicly available AI-powered offensive security framework
ARTEX (“AI 自主渗透测试系统,” or AI autonomous penetration testing system) is an AI-driven penetration testing platform. A Go-based backend coordinates multiple large language model (LLM) agents that can take an attack from reconnaissance and attack surface discovery through exploitation, verification, and reporting, with little or no human involvement. ARTEX includes an embedded Next.js web interface and uses PostgreSQL for storage.
ARTEX is primarily a web application penetration testing tool. Its built-in guidance, skills, and findings categories center on vulnerabilities in HTTP applications and APIs, including SQL injection, server-side template injection, XML external entity (XXE) injection, file upload flaws, authentication bypass, and insecure direct object references (IDOR).
ARTEX agents also perform general network reconnaissance and credential attacks. After agents gain initial access to a system or network, they can pivot through interactive shells. By default, ARTEX does not take any measures to obfuscate its malicious activity.
In July 2026, GitHub user Autumn-27 published ARTEX as open-source code with a Chinese-language interface. While the original developer removed the source code in October 2026, other developers who had forked the project continue to publish their own versions of ARTEX in many other languages. In November 2026, the China-based cybersecurity company ThreatBook (微步在线) claimed ownership of ARTEX and began offering commercial access to “ARTEX Pro”, in addition to CyberStrikeAI Enterprise Edition and other AI-powered penetration testing frameworks.
## AI agent architecture
ARTEX uses multiple AI agents for different functions. The threat actor defines the target scope, and a goals model breaks the engagement into objectives that can be verified. A planner agent continuously reviews a knowledge graph containing discovered assets and findings, then issues short attack directions called “intents.” Worker agents claim those intents and carry them out with a real shell and offensive tools. They write new assets, facts, and confirmed vulnerabilities back to the graph. Each update wakes the planner agent, which decides what to do next. The cycle continues until the goals are met or the task reaches its time or step limit. A reporter agent then documents each confirmed finding with reproduction steps and a proof of concept.
[image: Diagram of ARTEX agent architecture, including goals agent, planner agent, worker agents, and reporter agent. ]
ARTEX AI agent architecture
The threat actor can configure ARTEX to power its agents with virtually any large language model, including frontier models, open-weight models, or models that the threat actor has abliterated (modified to remove built-in guardrails) or otherwise manually tuned. For that reason, ARTEX activity is not necessarily constrained by any single provider’s safety controls or visible in any single provider’s telemetry.
An optional pool function allows ARTEX to switch to different models when one fails for any reason (for example, quota exhausted, invalid key, rate-limited, or erroring). The function includes a configurable priority order and cooldown, so a long campaign can continue across multiple providers or keys.
## Capabilities
ARTEX agents call tools to act on intents. While threat actors and agents can add arbitrary tools, ARTEX includes a set of pre-configured tools that define its core capabilities: network reconnaissance, web application mapping, web shell upload, and web browser-based attacks.
- nmap — A network discovery and port-scanning tool that identifies systems, exposed services, and often their versions, rather than simply testing one connection
- nc (netcat) — A general-purpose network utility for opening TCP or UDP connections, listening on ports, and moving raw data between systems
- telnet — A basic interactive TCP client useful for manually probing text-based services
- whois — A registration-data lookup tool that retrieves information about domain names or IP address allocations
- dig — A DNS diagnostic tool
- curl — A command-line HTTP and protocol client suited to crafting requests and inspecting responses, including headers, authentication, and APIs
- wget — A web download utility
- Playwright + Chromium — A browser-automation stack that drives a real Chromium browser, with all elements of the HTTP exchange exposed for manipulation
- node — A JavaScript runtime
- python3 — A general-purpose scripting runtime
- git — A tool for retrieving and inspecting code repositories and their history
- ripgrep — A fast recursive text-search tool for finding strings or patterns
- jq — A command-line JSON processor that filters and transforms structured output from APIs and other tools
Threat actors also commonly add exploitation frameworks and credential attack tools to extend the capabilities of ARTEX agents:
- sqlmap — A specialized web-application testing tool that detects and assesses SQL injection in application inputs
- hydra — A parallelized credential-testing tool supporting many network login protocols and configurable username/password combinations
- medusa — A modular, parallel network-login tester distinguished by its service-specific authentication modules
- ncrack — A network authentication testing tool from the Nmap ecosystem, focused on high-speed testing of supported remote services
- nuclei — A template-driven vulnerability scanner that checks targets for defined exposures, misconfigurations, and known issues across multiple protocols
- nikto — A web-server scanner focused on potentially dangerous files, outdated components, and common server misconfigurations
- gobuster — A wordlist-based discovery tool that enumerates web paths, DNS subdomains, or virtual hosts with a relatively focused command-line workflow
- ffuf — A flexible web fuzzer that substitutes candidate values into chosen parts of a request, such as paths, parameters, headers, or hostnames
- Msfconsole (Metasploit) — An exploitation framework and its interactive console, combining exploit modules, payloads, and post-exploitation workflows in one environment.
- john (John the Ripper) — An offline password-auditing tool notable for broad hash-format support and adaptable cracking modes
- hashcat — An offline password-recovery tool distinguished by GPU-accelerated candidate generation and hash testing

- Server-side template injection

- File upload flaws

- Credential attacks
- Weak-password testing
- Password spraying
- Brute force guessing
- Abuse of account-recovery flows

- Credential access

- Adding application credentials for persistence

## Identifying ARTEX network activity
While ARTEX does not invent new attack techniques, it can combine the adaptable attack chain of a human threat actor with the speed and precision of malicious software. Therefore, the challenge of identifying network activity from AI-driven tools like ARTEX is differentiating it from both human- and software-driven activity.
Defenders can detect three types of evidence that may suggest AI-driven activity:
- The most durable signal of AI-driven activity is the pattern formed by the bursts of machine speed activity. ARTEX agents, sometimes working in parallel, continually adapt and retry a given tactic until they succeed or run out of time. ARTEX agents quickly and exhaustively iterate through different methods of access, exploitation, or abuse. A human threat actor takes time to move from one stage of the attack chain to the next. In contrast, after successfully compromising a system or credentials, the framework then dispatches additional agents to move on to the next stage of the activity at machine speed. While ARTEX is a popular tool, other AI-driven offensive security frameworks also generate similar patterns of behavior.
- Automated penetration testing tools, including the ones that ARTEX agents call, can produce a characteristically large volume of anomalous traffic from a single source in a short time. ARTEX does not obfuscate its malicious activity; a large number of these traffic bursts occurring at intervals is consistent with automated targeting.
- A small amount of traffic might have user agent strings, network protocol options, or other default values strongly associated with ARTEX or the tools it calls. However, threat actors and ARTEX agents frequently change these values, particularly when evading static rules that block such values. The following table shows two such user agent strings specific to ARTEX:
TypeValueNotes
User agent stringartex-enrich/*Included with a short GET request to each newly discovered web asset that does not follow redirects, closes the connection, and reads only enough of the response to extract the page title.
User agent stringnorma/*Included with requests made directly by agents through their built-in web-fetch tool rather than through shell tools.
Defensive honeypots [108], decoys, tarpits, and fake wins can pull autonomous AI attacks away from legitimate targets. Honeypots and decoy surfaces such as Microsoft Sentinel Deception [109] give the agent attractive but worthless targets to pursue. Tarpits consume the agent’s time and budget. Fake wins present convincing evidence that the agent’s objective is complete, which can cause it to stop on a false success. Honeytokens can provide early warnings of AI compute hijacking. In Microsoft’s testing, these controls helped reduce the attack traffic reaching real assets and produced high-confidence, attribution-quality signal.
## Identifying ARTEX system activity
After gaining initial access to a system, ARTEX agents often use well-known risky utilities (for example, certutil, curl, wget, netcat) on the system to launch web shells, install remote access trojans (RATs), or take other action to achieve persistence. Because ARTEX does not take any measures to obfuscate its malicious activity, existing methods for detecting compromise will likely capture ARTEX activity:
- Web server processes (such as w3wp.exe, php-fpm, httpd or apache2, or Java application servers) starting sh, bash, cmd.exe, or PowerShell
- New or modified script files (.php, .jsp, .jspx, .asp, .aspx, or .ashx) in web-accessible or upload directories; this includes files written by a database server process after its logging settings were changed to point a log file at a web directory
- Several short-lived web shells with incrementing names, each running a different command, as ARTEX agents correct errors until a web shell runs cleanly
- Rapid reads of /etc/shadow, .env and configuration files, private keys, and cloud credential files, and bursts of database extraction
- Reverse shells and outbound requests from the server to webhook or file-sharing services used to deliver scripts and return command output
- Two or three attack chains active at once, and renewed attempts through new paths after containment
## Mitigation and protection guidance
Microsoft recommends the following mitigations to reduce the impact of this threat. Check the recommendations card for the deployment status of monitored mitigations.
ARTEX doesn’t introduce new attack techniques. It runs common penetration testing tools and tries one approach after another at machine speed. The mitigations that matter most close exposure before scanning finds it, slow down bursts of requests, protect credentials and application secrets, and contain a compromise automatically.
### Reduce internet-facing exposure
- Find and fix exposed assets first by using Microsoft Defender External Attack Surface Management discovery [110] to inventory the internet-facing hosts, websites, and services you own, including ones you didn’t know about. Then prioritize fixes with Microsoft Defender Vulnerability Management [111], which shows internet-exposed resources that lead to sensitive data or privileged identities. ARTEX agents start with port scans and web path enumeration and act on whatever they find.
- Block and slow down attacks on web applications and APIs. After tuning in detection mode, switch Web Application Firewall on Application Gateway [112] to prevention mode so that SQL injection and other common web attacks are blocked, not only logged. Add rate limiting on Application Gateway [113] or rate limiting on Azure Front Door [114] to cap how many requests one client can send in a short time, and turn on bot protection [115] to block or log requests from known malicious IP addresses. For APIs in Azure API Management, follow Mitigate OWASP API security top 10 threats [116] to enforce authentication, object-level authorization, and rate limits. ARTEX agents send hundreds of requests to learn which paths a server allows and harvest API documentation to find internal routes, then test them for injection, authentication bypass, and access-control flaws.
### Map and test attack paths
- Map what an exposed asset or stolen credential could reach before an agent does. Use attack paths in Microsoft Security Exposure Management [117] and attack path analysis in Defender for Cloud [118] to find defensive choke points, where paths to critical assets converge, and explore the blast radius of each one. Classify your critical assets [119] so the paths are complete, and query the enterprise exposure graph [120] in advanced hunting to explore the same connections. During an incident, blast radius analysis in the incident graph [121] shows the paths an attacker could take from a compromised entity to a critical asset. ARTEX agents record the assets and vulnerabilities they discover in a graph [122], so mapping your own graph first shows where they would go next.
- Test the paths that matter most, within Microsoft’s rules. Microsoft recommends regular red team operations [123] to complement vulnerability scanning. Agree on the scope and constraints with resource owners and fix all critical findings. Testing of Azure resources must follow the penetration testing rules of engagement, [124] which encourage testing your security monitoring and detection, prohibit automated testing that generates excessive traffic, and prohibit using secrets that aren’t your own, including publicly leaked ones [125]. Agentic tools like ARTEX scan public code repositories for secrets [126], so decide before testing how testers will handle credentials that belong to someone else.
- Organizations can incorporate Microsoft Perception’s [127] Recon Agent [128] to map relationships between Azure resources, Microsoft Entra ID identities, and permissions to identify potential lateral movement paths, privilege escalation opportunities, and high-value assets accessible following an initial compromise. Recon Agent’s Identify attack paths [129] playbook searches for potential attack paths within an Azure subscription, while the Assess identity risks [130] playbook investigates whether a managed identity could provide a path to critical assets. The Protect against a threat [131] playbook correlates identified exposures with relevant threat intelligence. Because Perception’s Recon Agent performs read-only analysis rather than active exploitation, organizations should complement its findings with authorized penetration testing to validate viable attack paths.
### Protect web servers
- Run endpoint protection on every internet-facing server and keep it blocking. Use Defender for Endpoint on Linux [132] and the Defender for Servers plan [133] so that the endpoint detections and hunting queries in this report cover the servers that ARTEX agents exploit, including Linux servers. Turn on tamper protection [134], use EDR in block mode [135] on Windows devices that run a non-Microsoft antivirus product, and turn on the Block Webshell creation for Servers [136] attack surface reduction rule on Exchange servers.
- Restrict outbound connections from web servers. Allow only the destinations each server needs, for example with Azure Firewall threat intelligence-based filtering [137], and create indicators for IPs, URLs, and domains [138] in Defender for Endpoint to block known-bad destinations. ARTEX agents have used curl and netcat to download remote access trojans, and curl with rotating webhook.site URLs to deliver scripts and return command output.
### Secure accounts and sign-ins
- Apply Conditional Access to every user and workload identity. Create policies that require multifactor authentication (MFA) for all users [139], enforce phishing-resistant MFA for administrators [140], and block legacy authentication [141]. Consider wider adoption of phishing-resistant passwordless authentication deployment [142] to all users. Configure risk policies in Microsoft Entra ID Protection [143] to require MFA or block access for medium-risk and high-risk sign-ins; sign-ins from known threat actor infrastructure, including infrastructure behind ARTEX activity, raise Verified threat actor IP detections at high risk.
- For service principals, use Conditional Access for workload identities [144] to block sign-ins from unexpected locations or with elevated risk; workload identity risk detections [145] flag leaked credentials and suspicious sign-ins, including credentials found in public code on GitHub.
- Ban weak passwords and slow down guessing. Turn on Microsoft Entra Password Protection [146] with a custom banned password list, extend it to on-premises Active Directory [147], and review smart lockout [148] settings. In one Storm-0940 campaign that used ARTEX, Microsoft recorded more than 151,000 failed sign-ins, peaking at 2,900 failures per minute.
### Protect application secrets and privileges
- Keep application secrets out of code and replace any that leak. Use application management policies [149] to limit which kinds of secrets and certificates apps can use and to enforce rotation, and move workloads to managed identities [150] where possible. Turn on secret scanning and push protection [151] for Azure DevOps repositories and secrets scanning in Defender for Cloud [152] for virtual machines and cloud deployments and invalidate and replace any secret found in code or configuration files, including .env files. In one case [153] that Microsoft observed, an AI agent went from searching GitHub for client secrets to taking data from Azure Key Vault in five minutes.
- Govern app registration, consent, and privileged roles by restricting app registration [154] to the users who need it, configuring user consent [155] so that users can’t grant broad permissions to unverified apps, and using app governance in Microsoft Defender for Cloud Apps [156] to see which apps can reach your data. Use Privileged Identity Management [157] for time-bound role activation, and monitor application credential changes and role assignments as described in the Microsoft Entra security operations guide for applications [158]. During Storm-0940 activity, ARTEX agents added credentials to applications, and an application assigned itself the Global Administrator role.
### Protect cloud resources and data
- Limit what a stolen credential or token can reach. Follow best practices for Azure RBAC [159] to limit each service principal to the resources and operations its application needs, and grant managed identities only the access they need [160] so that a token taken from the Azure Instance Metadata Service [161] through an XXE or SSRF flaw can’t reach other resources. ARTEX agents map the permissions of the credentials they capture and have used an XXE flaw to query a cloud metadata service for role credentials, and in one investigation AI agents used a compromised OAuth application to run scripts on Azure virtual machines.
- Harden and monitor the services that hold secrets and data. Follow Secure your Azure Key Vault [162]; for storage accounts, prevent Shared Key authorization [163] and remediate anonymous read access to blob data [164]; disable basic authentication [165] for App Service publishing; and disable local authentication [166] so that Foundry Tools accept only Microsoft Entra ID authentication. Then turn on Defender for Key Vault [167], Defender for Storage [168], Defender for Resource Manager [169], Defender for App Service [170], Defender for open-source relational databases [171], and AI threat protection [172] for the workloads you run. ARTEX agents have run commands through cloud administration interfaces such as Kudu when they had credentials for them, and AI agents have focused on credentials for AI services.
### Limit lateral movement and contain attacks automatically
- Detect credential theft on domain controllers. Install Microsoft Defender for Identity sensors [173] on all domain controllers. Its alerts, listed in the Detections section, cover the Active Directory credential theft and reconnaissance that ARTEX agents run in compromised domains.
- Remove reusable passwords and standing access. Use group managed service accounts [174], whose passwords Windows manages automatically, so that service accounts don’t rely on passwords that people choose and rarely change. Use Windows LAPS [175] to rotate each device’s local administrator password so that one captured password doesn’t work across many devices and use just-in-time machine access [176] in Defender for Cloud to keep management ports such as RDP and SSH closed until they’re needed. ARTEX agents reuse captured credentials to move laterally over SSH and WinRM.
- Enable automatic attack disruption [177] to contain compromised assets that an attacker is using and limit lateral movement early, as well as automated investigation and response [178], which investigates and remediates alerts automatically. In multiple ARTEX-driven Storm-0940 intrusions, privileged access came less than three hours after initial targeting.

## Hunting
### Audit logs and investigation data
Detecting and investigating ARTEX activity depends on logs that some organizations don’t collect by default. An empty result from a hunting query isn’t proof that no access occurred if the underlying logs aren’t collected.
- Microsoft Entra logs. Use Microsoft Entra diagnostic settings [194] to send audit logs and sign-in logs to a Log Analytics workspace. Service principal sign-ins [195] are recorded separately from interactive user sign-ins, so include them.
- Microsoft Graph requests. Microsoft Graph activity logs [196] record the requests that applications and users send to Microsoft Graph, including the user agent, which helps scope reconnaissance with stolen application credentials.
- Web server logs. Collect IIS logs [197] with Azure Monitor and turn on App Service diagnostic logs [198] so that request bursts and user agents are available for hunting.
- Web application firewall activity. Web Application Firewall logs [199] on Application Gateway include access and firewall logs for allowed and blocked requests.

### Microsoft Defender XDR
Microsoft Defender XDR customers can run the following advanced hunting [201] queries to find related activity in their networks. The first three queries require Microsoft Defender for Endpoint on the Windows and Linux servers that host internet-facing applications. The service principal query uses the EntraIdSpnSignInEvents table, which requires Microsoft Entra ID P2.
Web server processes running bursts of shell commands
Find web and application server processes that start shells or download tools many times within five minutes. ARTEX agents run commands through web shells and retry at machine speed and have used curl and netcat to download remote access trojans. Tune the threshold, set to 10 distinct commands by default, and exclude build or automation servers that run shells under Java or Node.js.
// Shells and download tools started by web or application server processes let WebServerProcesses = dynamic(["w3wp.exe", "httpd", "apache2", "nginx", "lighttpd", "java", "node"]); let ShellsAndTools = dynamic(["sh", "bash", "dash", "zsh", "cmd.exe", "powershell.exe", "pwsh", "pwsh.exe", "curl", "wget", "nc", "ncat", "certutil.exe", "python3", "perl"]); DeviceProcessEvents | where InitiatingProcessFileName in~ (WebServerProcesses) or InitiatingProcessFileName startswith "php" | where FileName in~ (ShellsAndTools) | summarize DistinctCommands = dcount(ProcessCommandLine), Tools = make_set(FileName, 20), SampleCommands = make_set(ProcessCommandLine, 25), FirstSeen = min(Timestamp), LastSeen = max(Timestamp) by DeviceId, DeviceName, InitiatingProcessFileName, bin(Timestamp, 5m) | where DistinctCommands >= 10 | order by DistinctCommands desc
Script files written to web folders by web or database server processes
Find script files, such as .php, .jsp, and .aspx files, that web or database server processes create or change, including several files in a short time. ARTEX agents upload web shells with incrementing names and have written web shells through database log files. Content management system updates also write script files, so review the file names and folders.
// Script files created or changed by web server or database server processes let ScriptExtensions = dynamic(["php", "phtml", "jsp", "jspx", "asp", "aspx", "ashx", "asmx"]); let WebServerProcesses = dynamic(["w3wp.exe", "httpd", "apache2", "nginx", "lighttpd", "java", "node"]); let DatabaseProcesses = dynamic(["mysqld", "mariadbd", "postgres", "sqlservr", "sqlservr.exe"]); DeviceFileEvents | where ActionType in ("FileCreated", "FileModified", "FileRenamed") | extend Extension = tolower(extract(@"\.([^.]+)$", 1, FileName)) | where Extension in (ScriptExtensions) | where InitiatingProcessFileName in~ (WebServerProcesses) or InitiatingProcessFileName in~ (DatabaseProcesses) or InitiatingProcessFileName startswith "php" | summarize Files = dcount(FileName), FileNames = make_set(FileName, 25), Folders = make_set(FolderPath, 10), DatabaseWrites = countif(InitiatingProcessFileName in~ (DatabaseProcesses)) by DeviceId, DeviceName, InitiatingProcessFileName, bin(Timestamp, 10m) | where DatabaseWrites > 0 or Files >= 3 | order by DatabaseWrites desc, Files desc
Commands that read several kinds of credential and secret files
Find devices where commands reference three or more kinds of credential and secret files within 10 minutes, such as /etc/shadow, .env files, private keys, and cloud credential files. ARTEX agents read these files in rapid succession after they gain a foothold.
// Commands that reference three or more kinds of credential and secret files let SecretFiles = dynamic(["/etc/shadow", ".env", "id_rsa", "id_ecdsa", "id_ed25519", ".aws/credentials", ".azure/", ".kube/config", ".git-credentials", ".pgpass", ".my.cnf", "wp-config.php", "web.config", "appsettings.json"]); DeviceProcessEvents | where ProcessCommandLine has_any ("shadow", "env", "id_rsa", "id_ecdsa", "id_ed25519", "credentials", "azure", "kube", "pgpass", "cnf", "config", "appsettings") | extend SecretFile = SecretFiles | mv-expand SecretFile to typeof(string) | where ProcessCommandLine contains SecretFile | summarize SecretFileTypes = dcount(SecretFile), SecretFilesSeen = make_set(SecretFile), SampleCommands = make_set(ProcessCommandLine, 20), FirstSeen = min(Timestamp) by DeviceId, DeviceName, AccountName, bin(Timestamp, 10m) | where SecretFileTypes >= 3 | order by SecretFileTypes desc
Service principal sign-ins for several applications from one IP address
Find IP addresses that attempt service principal sign-ins for three or more applications in an hour with both failures and successes, or that send the default ARTEX user agents. Agentic tools have used leaked application credentials across many applications and tenants. Error codes 7000215 and 7000222, an invalid or an expired client secret, show attempts with a credential for the application. When a success follows those failures from the same address, investigate right away.
// Service principal sign-ins for several applications from one IP address EntraIdSpnSignInEvents | where IsManagedIdentity == false | summarize ServicePrincipals = dcount(ServicePrincipalId), SucceededFor = dcountif(ServicePrincipalId, ErrorCode == 0), FailedSignIns = countif(ErrorCode != 0), InvalidOrExpiredSecret = countif(ErrorCode in (7000215, 7000222)), ArtexUserAgent = countif(UserAgent has_any ("artex", "norma")), Applications = make_set(ServicePrincipalName, 20), Resources = make_set(ResourceDisplayName, 20), UserAgents = make_set(UserAgent, 10), FirstSeen = min(Timestamp), LastSeen = max(Timestamp) by IPAddress, bin(Timestamp, 1h) | where (ServicePrincipals >= 3 and SucceededFor >= 1 and FailedSignIns >= 1) or ArtexUserAgent > 0 | order by ServicePrincipals desc
### Microsoft Sentinel
These queries require Microsoft Entra ID audit logs, and IIS logs, App Service HTTP logs, or Application Gateway access logs in the workspace.
Machine-speed web request bursts and default ARTEX user agents
Find client IP addresses that request 100 or more distinct paths with 50 or more client errors in one minute, or that send the default ARTEX user agents, artex-enrich and norma. The query also flags the default user agents of tools that ARTEX runs, such as curl, Wget, Python HTTP clients, headless Chromium, and Nmap. Those are common in legitimate automation, so don’t alert on them alone.
// Requests per client IP per minute, with default ARTEX and tool user agents flagged union isfuzzy=true (W3CIISLog | project TimeGenerated, LogSource = "IIS", ClientIP = cIP, Path = csUriStem, Status = tostring(scStatus), UserAgent = csUserAgent, Target = Computer), (AppServiceHTTPLogs | project TimeGenerated, LogSource = "App Service", ClientIP = CIp, Path = CsUriStem, Status = tostring(ScStatus), UserAgent, Target = CsHost), (AGWAccessLogs | project TimeGenerated, LogSource = "Application Gateway", ClientIP = ClientIp, Path = RequestUri, Status = tostring(HttpStatus), UserAgent, Target = Host) | extend AgentType = case( UserAgent has_any ("artex", "norma"), "ARTEX default", UserAgent matches regex @"^(curl|Wget|python-requests|Python-urllib|Go-http-client)/", "Tool default", UserAgent has_any ("HeadlessChrome", "Nmap"), "Tool default", "Other") | summarize Requests = count(), DistinctPaths = dcount(Path), ClientErrors = countif(Status startswith "4"), ArtexAgentRequests = countif(AgentType == "ARTEX default"), ToolAgentRequests = countif(AgentType == "Tool default"), UserAgents = make_set(UserAgent, 10), Targets = make_set(Target, 10) by ClientIP, LogSource, bin(TimeGenerated, 1m) | where ArtexAgentRequests > 0 or (DistinctPaths >= 100 and ClientErrors >= 50) | order by ArtexAgentRequests desc, DistinctPaths desc
Application credential changes and role assignments by the same identity
Find users or applications that both add or change application credentials and assign directory roles or application permissions within an hour. During Storm-0940 activity, ARTEX agents added credentials to applications, and an application assigned itself the Global Administrator role.
// Credential changes and role assignments made by the same identity within an hour AuditLogs | where Result =~ "success" | where OperationName in ("Add service principal credentials", "Add member to role", "Add app role assignment to service principal") or OperationName contains "Certificates and secrets management" | extend Stage = iff(OperationName has_any ("credentials", "Certificates"), "Credential", "Role") | extend ActorUpn = tostring(InitiatedBy.user.userPrincipalName), ActorServicePrincipalId = tostring(InitiatedBy.app.servicePrincipalId), ActorAppId = tostring(InitiatedBy.app.appId), TargetName = tostring(TargetResources[0].displayName) | extend Actor = coalesce(ActorUpn, ActorServicePrincipalId, ActorAppId) | summarize Stages = make_set(Stage), Operations = make_set(OperationName), Targets = make_set(TargetName, 20), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated) by Actor, ActorAppId, bin(TimeGenerated, 1h) | where array_length(Stages) == 2 | order by FirstSeen desc
## MITRE ATT&CK techniques
This tool has exhibited use of the following attack techniques. For standard industry documentation about these techniques, refer to the MITRE ATT&CK framework [202].
Resource Development
- T1588.007 Obtain Capabilities: Artificial Intelligence [203] | Threat actors obtain ARTEX from public repositories or forks and pair it with commercial or self-hosted LLMs.
- T1588.002 Obtain Capabilities: Tool [204] | ARTEX agents install offensive tools at runtime or write equivalent scripts.
Reconnaissance
- T1595.001 Active Scanning: Scanning IP Blocks [205] | ARTEX runs nmap for port and service scanning.
- T1595.002 Active Scanning: Vulnerability Scanning [206] | ARTEX agents probe web applications and APIs for injection, authentication, and access-control weaknesses.
- T1595.003 Active Scanning: Wordlist Scanning [207] | ARTEX agents enumerate directories, endpoints, and file names, sending hundreds of requests to learn which ones the server allows.
- T1594 Search Victim-Owned Websites [208] | ARTEX agents harvest JavaScript bundles, source maps, runtime configuration, and API documentation from target applications to discover internal API routes, and ARTEX’s enrichment component collects page titles from discovered sites.
Initial Access
- T1190 Exploit Public-Facing Application [209] | ARTEX agents exploit injection, file upload, authentication, and access-control flaws in internet-facing applications.
- T1078 Valid Accounts [210] | ARTEX reuses credentials that it captures, or that the operator supplies, against applications, hosts, and services.
- T1078.004 Valid Accounts: Cloud Accounts [211] | ARTEX agents authenticated to Microsoft 365 tenants with stolen application credentials that Storm-0940 supplied.
- T1199 Trusted Relationship [212] | ARTEX agents reached downstream tenants through an already-consented third-party application whose credentials Storm-0940 had stolen.
Execution
- T1059 Command and Scripting Interpreter [213] | ARTEX runs shell, Python, and PowerShell commands on compromised servers through command injection, web shells, and remote shells.
- T1651 Cloud Administration Command [214] | ARTEX agents have run commands through cloud administration interfaces, such as Kudu, when they had credentials for them.
Persistence
- T1505.003 Server Software Component: Web Shell [215] | ARTEX uploads web shells, or writes them through database logging, and then sends commands to them.
- T1098.001 Account Manipulation: Additional Cloud Credentials [216] | ARTEX agents added credentials to applications to maintain access during Storm-0940 activity.
Privilege Escalation
- T1098.003 Account Manipulation: Additional Cloud Roles [217] | ARTEX agents assigned privileged roles during Storm-0940 activity, including an application assigning itself the Global Administrator role.
Credential Access
- T1110.001 Brute Force: Password Guessing [218] | ARTEX tests weak passwords and brute forces sign-in forms.
- T1110.003 Brute Force: Password Spraying [219] | Storm-0940 used ARTEX to accelerate password spraying against Microsoft 365, and other actors have used it to spray identity providers.
- T1552.001 Unsecured Credentials: Credentials In Files [220] | ARTEX reads .env files, configuration files, and keys after gaining a foothold.
- T1003.008 OS Credential Dumping: /etc/passwd and /etc/shadow [221] | ARTEX reads /etc/shadow on compromised Linux servers.
- T1552.005 Unsecured Credentials: Cloud Instance Metadata API [222] | ARTEX agents have used an XXE flaw to query a cloud metadata service for role credentials.
- T1558.003 Steal or Forge Kerberos Tickets: Kerberoasting [223] | ARTEX agents run Kerberoasting scripts in compromised domains.
- T1003.006 OS Credential Dumping: DCSync [224] | ARTEX agents run DCSync scripts to obtain domain credentials.
Discovery
- T1087.004 Account Discovery: Cloud Account [225] | ARTEX agents performed Microsoft Graph and directory reconnaissance during Storm-0940 activity.
- T1087.002 Account Discovery: Domain Account [226] | ARTEX agents enumerate Active Directory objects, including privileged groups.
- T1580 Cloud Infrastructure Discovery [227] | ARTEX agents map the permissions of stolen cloud credentials and enumerate cloud resources.
Lateral Movement
- T1021 Remote Services [228] | ARTEX agents capture credentials for other reachable systems and move laterally through remote services such as Secure Shell (SSH) and WinRM.
Collection
- T1213.006 Data from Information Repositories: Databases [229] | ARTEX extracts database contents through SQL injection, such as with sqlmap, or with database clients.
- T1530 Data from Cloud Storage [230] | ARTEX agents perform mass reads from cloud storage with stolen credentials.
Command and Control
- T1090 Proxy [231] | ARTEX can send target traffic through a configured outbound proxy. Threat actors have rotated through virtual private network (VPN), proxy, and Tor infrastructure when blocked.
- T1102.002 Web Service: Bidirectional Communication [232] | ARTEX agents have used curl with rotating webhook.site URLs to deliver scripts to a compromised server and return command output.
