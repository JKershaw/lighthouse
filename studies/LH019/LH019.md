# What do the official PHP moving image tags name over time?

**Study:** LH019, version 0.1, 21 October 2026. **Status:** first baseline, later checkpoints not yet observed. **Written by:** Codex, GPT-6 Sol in ChatGPT Work Mode. **Protocol:** commit `4698c8e`, before any moving-tag result was read. **Observation window:** 21 October 2026, 17:12:59–17:14:43 UTC. **Model spend:** unknown in this harness; no paid external API. **Overlap:** LH018's same security episode and four version-specific reference images; these are reused comparisons, not independent releases.

## Answer

At the first reading, each of four preselected moving tags in the official PHP Docker Hub repository named the **same linux/amd64 manifest digest** as its LH018 version-specific, same-variant counterpart. Each manifest and configuration blob was retrieved, its content verified against its SHA-256 digest, and the configuration declared the corresponding fixed PHP source version. The moving tags were first observed *after* their current manifests had been pushed. This baseline cannot say whether they briefly named older images after the fix release, when a pointer changed, whether the built executable is patched, or whether anyone pulled or ran an image.

LH018 observed the corresponding fixed-version tags about 23–25 minutes before these moving tags, so equality now does not show they were equal then.

## Method

The [brief](brief.md) fixed four exact aliases and linux/amd64 before the collector read any. Variants match LH018's chosen version-specific tags so a digest comparison has the same image type. At each Hub tag URL, the collector retained the response and selected the linux/amd64 digest. An ephemeral anonymous bearer was used to retrieve exactly that OCI manifest and its referenced configuration, then discarded. The [read log](data/snapshot-2026-10-21/read_log.csv) records all 16 requests, including four token requests without bearer bodies, and hashes for the 12 retained response bodies. The [offline replay](scripts/analyse.py) checks every retained hash, verifies each manifest and configuration against its OCI digest, reconstructs the [four-row summary](data/summary-2026-10-21.csv), and compares the corresponding LH018 source responses. It downloaded 78,529 retained bytes, used four counted manifest GETs, and remained below the run's 20-request and 10 MiB ceilings. All four tracks answered. [Sources and their boundary](sources.md) were fixed with the brief.

## Limits

- This was selected after the PHP release, and all four moving tags already named the fixed-version manifests when Lighthouse first saw them. Earlier pointer states are lost to this instrument. No duration from release to tag update can be derived.
- The variants differ between branches; the four Hub push fields do not support a controlled branch-speed comparison. Manifest equality is stronger than matching tag names, but no layer or binary was inspected. Registry publication is not pull share or running PHP adoption.
- A later unchanged digest says only that the two observed endpoints match; it cannot rule out a change and reversal between visits. If a later digest differs, the change lies somewhere between the two observations. Missing responses remain unknown.
- This is an intentional repeat view of LH018's episode, not a replication or an independent security event. The two CVEs share this episode.

## 22 October checkpoint

The first prospective checkpoint ran at 03:53:47–03:55:39 UTC on 22 October, earlier in the fixed UTC day than the baseline's clock time. [The retained read log](data/snapshot-2026-10-22/read_log.csv) records 16 requests and 78,541 retained bytes. Offline replay verified all four Hub responses, manifest and configuration digests, and declared versions; [the four-row summary](data/summary-2026-10-22.csv) has exact timestamps and paths. All four linux/amd64 manifest digests equal their 21 October observations, with declarations 8.5.12, 8.4.27, 8.3.36 and 8.2.35 respectively. This establishes endpoint equality at the two readings, not continuous availability or the state of other architectures.

The Hub tag-level `tag_last_pushed` fields now show 21 October 18:58:40, 22:07:37, 22:02:48 and 21:58:00 UTC, respectively, later than the baseline fields, while the selected platform-level digest and `last_pushed` did not change. A tag-level metadata update does not imply this platform image changed. The public deployment-glitch report in official-images issue #22546 is a separate source to audit; this checkpoint alone cannot date or quantify its effect.
