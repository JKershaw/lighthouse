# Five derived PHP image tags already declared fixed versions

**Study:** LH025, version 0.2, 30 October 2026 (version 0.1, 22 October). **Status:** closed; daily reads 22 to 28 October, five of seven partial. **Writer:** Codex, GPT-6 Sol in ChatGPT Work Mode (version 0.1); daily checkpoints from 23 October and version 0.2 by Claude Code driving and scheduled runs (Claude Opus 5.5), version 0.2 from the retained reads. **Protocol:** local commit `c428d97`, mirrored in PR #26 before new registry reads. **Observation:** 22 October about 06:29–06:31 UTC, exact times in [the read log](data/snapshot-2026-10-22/read_log.csv), then one read a UTC day through 28 October ([checkpoints](checkpoints/)). **Overlap:** this purposefully follows the same PHP episode as LH018–LH024; Drupal's selected tag and digest were already known through LH023. **Cost:** model spend unknown; no paid external API.

## Answer

At the first observation, all five preselected Docker Hub `library` application image tags exposed a linux/amd64 manifest and config declaring one of the fixed PHP source versions. They are current derived publisher artifacts, not evidence of when their moving tags first changed, whether their executable bytes were independently checked or whether any customer deployed them. All five tracks are left-censored with respect to the patch event, and the known Drupal track is a deliberate overlap with LH023.

**Over the week, to 28 October.** No read from 22 to 28 October showed any of the five tags declaring an older PHP version: all 16 configurations retained declare the same fixed version as at the first read. Each tag's linux/amd64 image changed at most once while it was being read: both Nextcloud tags between the reads of 22 October 06:30 and 23 October 17:42 UTC, and both WordPress tags between the reads of 27 October 12:38 and 28 October 12:38 UTC; the one rebuilt configuration of each pair that was read still declares the same PHP release. Drupal's tag did not change on the reads that reached it, the last on 25 October. The registry's anonymous rate limit cut five of the seven reads short, so after 25 October the panel saw only the two WordPress tags, and much of the week is unknown for the rest.

## Method

The [brief](brief.md) fixed five exact tags and architecture. The collector retained one Hub tag response, an OCI manifest by the selected platform digest and its configuration for each. It discarded anonymous bearer bodies and logged those requests. The run used 18 external requests, five counted manifest GETs and 138,285 retained bytes. [Offline replay](scripts/analyse.py) verifies all retained response lengths and hashes, matches the selected manifests and configs to their SHA-256 digests, and reconstructs five rows with the declared PHP versions. No layer was fetched or binary run. [Sources](sources.md) define the registry fields and their limits.

## Limits

- Every selected tag already declared a fixed version at first observation. The instrument cannot recover a former tag pointer or infer a release-to-rebuild duration from these fields alone. A publisher timestamp is a metadata claim, not independent observation at that historical instant.
- `PHP_VERSION` is an inherited or set configuration value; manifest and config integrity establishes the bytes read, not the behaviour of a running interpreter. None of these responses supplies a build's resolved upstream base digest or the number of pulls and deployments.
- These five tags were chosen by repository family and variant, with Drupal included after LH023 had already read it. They are not a sample of all PHP consumers, and five of five is not an uptake rate.

Tag-level push fields moved without a platform change four times (Drupal on 22 October 21:55:59, `nextcloud:apache` on 23 October 19:50:53, the two WordPress tags on 26 October 15:16:13 and 18:17:24); as far as this instrument shows these re-pushed the same linux/amd64 content, and other platforms in the tag's index, which the panel does not follow, may have changed. Every change seen was a rebuild on the same PHP release. Why each image was rebuilt (an application release, a base-image change or a routine rebuild) is not read. As an interpretation made after the reads, the WordPress rebuilds of 28 October came hours after the official `php` images were rebuilt overnight (LH019, version 0.2), which fits a rebuild on a new base image; no build record binding the two was read. An unchanged digest at two reads does not rule out a change and reversal in between, and a tag not read on a day is unknown that day, not unchanged.
