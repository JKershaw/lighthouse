# R-0022: review of "recipes-follow-the-pin"

Stage one, written from the full piece, its short form and the README's "Current focus" only; the study record, brief, data and other notes were not opened.

## What a reader would believe, written before reading the record

**Principal finding, said back.** When a Python project holds a library at an older version in a pin or lockfile, the container recipe it keeps usually installs from that file: 129 of the 167 cases fixed rules could decide (77 per cent), and over half however the 68 undecided fall (55 to 84). About half of the 469 moments kept no recipe at all. Exact pins were followed more often than lockfiles, which a build read in only half of decided cases.

**Observed.** Each project's files at its last commit before a library release, April 2025 to August 2026, classed by what each recipe's install command reads, under rules fixed beforehand from installer documentation; a program classed 614 of 731 builds, agents 117; a second reviewer agreed on 57 of 60.

**Explained.** How a pin fails to bind a build: `pip install .` never opens a lockfile; others install another requirements file or the package from PyPI. Only 2 of the 38 non-following cases were shown able to take the new release.

**Caused.** The install command decides whether a pin holds, so the earlier timings of pins mostly stand for what those projects' own recipes would build. The pin-versus-lockfile gap is described, not tested.

**Limits noticed.** No image seen built or run; 68 undecided; development recipes counted like release ones, and one dissenting recipe made a moment "not following" (84 per cent by main recipe alone); not a sample of all software; summaries say "recipes" where the body counts moments; status draft.
