Readings I had to make that the rules leave open, recorded here so the comparison can weigh them:

- A manifest whose dependencies are read from a T file (setuptools `dynamic` in aider, forgepair and talklib; `open('requirements.txt')` in bdi-kit, nucypher and an-website's setup.py) takes L's version from that T file, so `pip install .` and a wheel or sdist built from that project in a needed job are class 1 with that T file deciding.
- `pip install --no-deps .` (an-website build-source-tarball) installs no dependency, so no version of L comes from any file: class 2 (lock unused) by the letter of the sub-labels, not class 1.
- `pip install -c pip-constraints.txt <other packages>` where pip-constraints.txt is not in T but pins L: class 4 (another pinned file), since the brief does not resolve whether L is installed.
- A Python script the step runs is not read; where its command line names a T file (`zipapps_patched.py -r pip-requirements.txt`), it is a step the rules cannot decide that could have made the job class 1, so class 6 (script not read) replaces class 4.
- `uv sync` with no uv.lock in the tree resolves the manifest afresh; where the manifest in T carries an exact pin (dcspy) or a workspace member's manifest in T does (ai-parrot), the job is class 1 from the exact pin, not "may re-lock", because no T lock applies.
- An external action that builds or compiles the project (mypycify, grimoirelab's build action) whose installs cannot be read is class 6 (external) rather than class 5, because it could have installed from a T file.
