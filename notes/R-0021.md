### The three disagreements and their resolution

1. **P132-s1-0, edumfa, snapshot, L mako, T requirements.txt and uv.lock.** Script: class 5, other named packages only. Reviewer: class 2, lock unused. The builder stage runs COPY . . and python -m build, and the final stage copies /tmp/dist/*.whl from it and runs pip install /dist/*.whl. The brief counts "a wheel built from it in the build" among the project's Python requirements, and its multi-stage rule says a wheel copied from a stage in the path carries that stage's class. The wheel is built from pyproject.toml, which is not in T; read at the commit, it carries static exact pins and does not name mako (mako arrives through alembic), and setup.py only ships requirements.txt as a data file, so amendment 1 does not apply. requirements.txt and uv.lock, both in T, are in the context through COPY . . and no step reads them. Resolution: the reviewer is right; the build installs the project's requirements and takes nothing from T, class 2 (lock unused). The rule at fault: classify.py records a wheel that resolves to another stage as a neutral effect ("wheel from a stage or step in the build") instead of the project install of the stage that built it; the same-stage case goes to its project rule. The pair's class at the snapshot changes from "nothing of the project's requirements" to "not from the pinned file". The same rule gives the same class to P132-h1-0 at the head; the 13 other builds in the record with that effect are class 1 or 2 on other steps, so the rule's whole effect is edumfa's pair, at snapshot and head.

2. **P159-s1-0 and P162-h1-0, galaxy, .k8s_ci.Dockerfile at snapshot 2b06d179d95c and head a396860c90a6, L mako and cryptography.** Script: class 5, other named packages only (pip install virtualenv ansible==11.11.0). Reviewer: class 6, script not read. The recipe clones galaxy-docker-k8s at build time and runs ansible-playbook on its playbook with galaxy_virtualenv_command=virtualenv, then deletes parts of $SERVER_DIR/.venv and sets the final stage's PATH to $SERVER_DIR/.venv/bin: the server's Python environment is built by a file outside the repository. Class 6's reason "script not read" names an install "in a file outside the repository", and the brief's missing-evidence rule says unknown is never counted as a negative; class 5 would state that nothing of the project's requirements is installed, which the recipe's own lines contradict. Resolution: the reviewer is right, with the ambiguity recorded below, since ansible-playbook is not in the brief's list of installers and the script has no rule for it. Both pairs change from "nothing of the project's requirements" to "undetermined". All 12 builds in the record that run ansible-playbook are this one recipe at the snapshots and heads of galaxy's six pairs (P158 to P163), all class 5 by the script, so the rule's whole effect is those six pairs at snapshot and head.

### Ambiguities found in the rules

1. **Delegated installs.** The install-step definition names installers and "a script, Makefile target or task-runner task in the repository"; class 6's "script not read" names "a file outside the repository". A RUN of ansible-playbook on a playbook fetched in the build falls between them. An amendment could say that a tool outside the list acting on the project from a file outside the repository is class 6 (script not read), which is how both galaxy builds are resolved here.

2. **Build context from a bare "." or an unmatched wildcard.** Rule (2) takes the recipe's own directory when every COPY source exists there; "." exists everywhere, so benchmark/Dockerfile (P020-h1-0, judged) gets benchmark/ as context and is class 6 (would not build) by the letter, though from the root it would be class 1 by amendment 1. A wildcard that matches nothing (P079-h4-0, COPY pyproject.toml uv.lock*, script-decided) leaves rule (2) with no context, and rule (3) gives class 6 (context), though Docker accepts an unmatched wildcard beside a matched source and the root is the only directory where the COPY succeeds (class 1 there). Writer and reviewer applied the letter in both and agree; the record should call these "undetermined by rule", not builds that fail in fact.

3. **Sub-labels are not exclusive** (lock unused and other file both fit P307), so the check counts agreement by class; the brief's sub-label order should be stated if the sub-labels are reported.

4. **Installs at start from a run-time mount** (weblate, P450-h2-0 and P448-h2-0): the only install runs in the ENTRYPOINT inside a directory the build leaves empty and a volume fills. No rule covers it; both readings are class 6 (other).

5. **Head builds that install from a lock absent at the snapshot** (P185-h3-0, agentstack): S2's "checked against LH008's rules for L" was read by both as class 4 (another pinned file). The record should state that reading, since S2's head table depends on it.

Retaining those lines, or saying in Limits that they were read and not kept, would close the gap.
