# Instrument register

This file is the instrument register named in AGENTS.md and defined by the instrument record block in Lighthouse_Study_Templates.md (LH F05). One entry per instrument, in that form: what it detects, what it misses, its observation point, how it was calibrated, its overhead and the changes that would invalidate a comparison made across it. An entry describes the sensor itself; it is not a claim about what the sensor has observed, and it is added or amended only when an instrument is registered or changes.

## Instrument I-0001

```
instrument: I-0001                version: 0.1          owner: (blank; no owner has
                                                          been assigned to instruments yet)
```

**what it detects:** `harbour/hb export` (the `cmd_export` function in `harbour/hb`) is a read-only client of the one local Harbour server a Lighthouse session boots for itself, plus a plain file copy from that session's own scratch directory. Each run:

1. `GET /api/proxy/issues?limit=250` (proxy bearer token) into `issues.json`: up to 250 of the workspace's issues, one per ticket `hb load` filed, with the Linear-shaped fields Harbour's proxy returns (identifier, title, description, estimate, priority, state name and type, assignee, labels, relations, timestamps).
2. `GET /api/proxy/dispatch` (proxy bearer token) into `dispatches.json`: dispatch items known to the proxy (id, status, kind, issue identifier, target, dispatch/resolve/completion timestamps, feedback count, consumer poll timestamps), with a `total` and a `truncated` flag but no limit parameter sent; the one export so far held two dispatches and `truncated` read false, so the endpoint's behaviour once a workspace holds more has not been observed.
3. `GET /workspace/<key>/api/dispatch/history` (the session cookie jar, not a bearer token) into `history.json`: fuller dispatch entries, including the original prompt text, the requested model/harness/effort, and the whole feedback array per item verbatim: progress messages and the `[resources]`, `[usage]`, `[done]`/`[failed]` markers with their timestamps. This is the instrument's only route to feedback text.
4. `GET /api/proxy/north-star` (proxy bearer token) into `north-star.json`: the current north star text, a generated reading of drift against it (state, gap narrative, age in days), a roadmap state/narrative summary, and a document-version block.
5. `GET /workspace/<key>/api/roadmap/reports` (session cookie) into `roadmap-reports.json`: a list of saved roadmap report stubs (id, generatedAt, model, north star text) with no narrative body.
6. For every issue identifier found in step 1, `GET /api/proxy/issues/<identifier>/cost` (proxy bearer token), collected into `cost.json`: per-issue `pricedUsd`, `totalUsd`, a list of `unpriced` model names, `noTelemetryCount`, `noLineage`, a `workerSessions` array (each dispatch's model, harness, effort, duration and `costUsd`) and an `appCalls` block for Harbour's own feature-level calls attributed to that issue, over a 30-day rolling window. A failed per-issue read is caught and stored as `{"error": ...}` rather than stopping the export. In the one export so far, both `workerSessions` entries read `costUsd: null`, because that session's `[usage]` feedback carried only `model`, `harness` and `effort` with no token counts. `harbour/hb usage --latest` (and the `usage.py` script behind it) has since been extended to compute real input, output and cache token counts and a priced `costUsd` from the poster's own transcript, so a usage entry posted from today onward gives this same `cost.json` read a price the first export could not show; that is a difference in what later exports can detect, not a change to the instrument's code.
7. A filesystem copy, not an HTTP read, of any `next-run-*.json` and `roadmap-*.json` files already sitting in this session's local, git-ignored `harbour/.session/` directory: the saved output of `hb next` and `hb roadmap`, if either ran earlier in the same session. Nothing is fetched again at export time, so a session that never called `hb next` or `hb roadmap`, or whose session files were removed first, exports no roadmap or next-run content even though `roadmap-reports.json` may still list report metadata. This is how the one export so far carries a next-run suggestion set and a full roadmap narrative, and, under a `.json` name matched by the same copy pattern, the raw server-sent-event stream that produced that narrative (renamed to `.txt` on 26 September 2026 with no change to its content, per that export's own manifest note).
8. A `manifest.json` the script writes itself: the collection time (the export directory's own name, UTC, to the second), the Harbour commit the local instance was built from (`harbour/.session/harbour-commit`), the workspace key, and the sorted list of files written.

Before anything is written, the script redacts: it substitutes `[redacted]` for the literal dispatch-token and proxy-token strings read from the local session directory, and separately regex-redacts any `Bearer <30+ character token>` pattern, across every `*.json` file in the export directory, printing which files it touched. The one export so far triggered no redaction; the safeguard exists in the code but has not yet been exercised against a real credential.

It also round-trips ticket status: after writing the files above, it reads `issues.json` back, matches each Harbour issue to a Lighthouse ticket by title prefix (`"<ticket id> "`), maps the issue's state type (`backlog`, `unstarted`, `started`, `completed`, `canceled`) to the ticket's `status` field (`backlog`, `todo`, `started`, `done`, `done`) and rewrites `harbour/tickets.json` in place, printing how many ticket statuses changed.

**what it misses:** The proxy audit log: Harbour's own documentation states that calls through its workspace proxy are audit-logged (Lighthouse_Operating_Handbook.md, citing S12 in LH F02), but no read in `cmd_export` retrieves that log, and no export file contains an audit entry. Proxy events, named separately from the audit log in this ticket's own wording: no endpoint the script calls returns anything named "events" either, so this record can say only that they are not read here, not what they would contain. The driver's own tokens: the session that runs `harbour/hb` and orchestrates a drive is not measured by any of the reads above; only what a consumer posts back as `[usage]` feedback on its own dispatch appears in `history.json` and `cost.json`. `harbour/hb drivercost` can now compute the driver's own spend from its transcript, a capability added since this ticket was written, but that figure is not posted to Harbour by any step in the session procedure, so it remains absent from every export that exists. A workspace-level total of Harbour's own model spend: the roadmap, next-run and north-star-reading calls all draw on the OpenRouter key `hb up` provisions, `cost.json`'s `appCalls` are attributed per issue, and no proxy-reachable route sums this spend across the whole workspace (harbour/requests.md records this as not yet filed with Harbour); a call made outside any issue's attribution would not surface in this instrument at all. Coverage beyond the stated page sizes: `issues.json` is requested with `limit=250` and the script never follows `pageInfo.hasNextPage`; `dispatches.json` carries a `truncated` flag with no limit parameter sent; neither has been observed to truncate, because the one workspace so far has held a handful of issues and two dispatches. Any failed HTTP call: none of the five main reads checks a status code or passes `--fail` (only the per-issue cost loop and the token-mint calls in `hb up` do), so a cookie or token problem, or a server error, would write whatever body Harbour returned into that file without the export command failing or the manifest saying so. A structured link from a dispatch to the study record it served: the `[study]` feedback marker that would carry this (harbour/requests.md, "study marker", not yet built) does not exist yet, so today's feedback arrays convey that link only in prose, if at all. Anything about the machine that claims a dispatch: process activity, busy core seconds, requests by destination are I-0002's subject ("Sample the host"), not this instrument's; the `[resources]` entries this instrument does carry, inside `history.json`'s feedback arrays, are whatever a consumer chose to post, not an independent sample. Any session, dispatch or issue that existed only in a Harbour store that has since been discarded: each `hb up` starts a fresh, git-ignored file store, and nothing carries over between sessions except what an earlier export already committed to this repository.

**observation point and boundary:** The instrument sits at the HTTP boundary of one locally booted Harbour server (`http://localhost:$HARBOUR_PORT`, default 3123), reading only what that instance's proxy and workspace-session APIs return for the single workspace this session created. It is a snapshot at one moment, the export call, not a continuous feed; the roadmap and next-run content it carries is whichever output files happen to still be sitting in the local session directory at that moment, not a fresh read. It sees Harbour's account of the workspace; it does not see the host that ran a dispatch's agent, and it does not see Harbour's own database or process directly.

**sampling rule and interval:** Not periodic today. `hb export` is invoked once, by hand, at the end of a session (CLAUDE.md step 6), after tickets have been closed; nothing in the repository schedules it. Lighthouse_Harbour_Workspace_Plan.md's own text for this ticket anticipates a weekly cadence once Harbour is hosted persistently, so that no record ages past the thirty-day feedback and audit retention window Harbour's documentation states (Lighthouse_Operating_Handbook.md, citing S12). Today each container is itself ephemeral and each `hb up` starts a fresh store, so the effective cadence is once per session; the weekly rule does not yet apply, as the ticket that named this instrument says.

**calibration (known events, dates, result):** One known-event check exists. In the session of 25 September 2026, two Harbour issues (LOCAL-3, ticket LH000, and LOCAL-11, ticket Q-0002) were closed with `hb close` before `hb export` ran. The export's ticket round-trip correctly moved both tickets from `todo` to `done` in `harbour/tickets.json` (commit 7c5344e), matching the issue states Harbour reported, and no other ticket changed. No known-event test has yet been run against the endpoint reads themselves, for example deliberately triggering a redaction, a truncation or a failed HTTP status to see how the instrument behaves under each, and no repeated run exists to check stability across sessions. This is a single passing check of one code path, not a calibration in LH F02's standard-candle sense.

**expected overhead and how measured:** Expected to be small: five read-only GET requests against a local server, one further read per issue, a handful of small file writes and one file rewrite, all local to the container. This has not actually been measured; the script times nothing and records no byte count or duration of its own, and no host or wall-clock sample was taken around the one export that has run. The only figure available after the fact is the size of what it wrote: the one export directory (`harbour/exports/20260925T224443Z/`) holds 10 files totalling 65,358 bytes, for a session that ran two dispatches, measured now with `ls -la`, not by the script. One data point cannot establish a rate or a trend against dispatch count, session length or workspace size; it is reported as what is available, not as an overhead figure.

**changes that would invalidate comparisons:** A change to `cmd_export` itself, including which endpoints it calls, the `limit=250` cap, the redaction patterns, or the ticket-status mapping table. A change to Harbour's own API shapes, its retention windows or its state-type vocabulary; LH F02 already flags that S12 must be re-checked against the running version before a study relies on a field. A move from a fresh per-session local store to a hosted, persistent Harbour, which the ticket that names this instrument expects to bring the weekly cadence; a comparison spanning that move would set an ephemeral, once-per-session instrument against a periodic one over a persistent store, and the retention pressure that motivates the weekly cadence does not exist locally today. A future workspace-level Harbour spend endpoint, or a driver-cost figure that starts being posted back to Harbour: either would widen what `cost.json` or `history.json` can show with no change to this instrument's own code, so a comparison across that point would set instruments of different coverage against each other even though the exporting code was unchanged. Hand-editing `harbour/tickets.json` between exports outside the round-trip itself, which would confuse the changed-ticket count the script reports. Running more than one export within the same UTC second, which would collide on the collection-time directory name used as both the export's identifier and its timestamp.

**source retention window (if reading an external source):** Not an external source in the S1 to S19 sense; it reads Lighthouse's own Harbour instance. That instance's stated retention still bounds when this instrument must run: dispatch items expire after twenty-four hours, and feedback, status and audit records after thirty days (Lighthouse_Operating_Handbook.md, citing S12); an export must be taken before those windows close if it is to carry a given dispatch's feedback at all.
